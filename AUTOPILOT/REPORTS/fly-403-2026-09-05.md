# Fly.io 403 at the PM node — diagnosis and fix

**Date:** 2026-09-05
**Branch:** `fix/fly-create-app-403`
**Status:** code fix complete and green. **One manual step is still required from Aditya** (§8) —
the credential itself was deliberately not touched.

---

## 0. Two corrections to the brief, up front

The brief asked me to say so loudly if the evidence disagreed. It does, in two places. Neither
changes the fix, but both change what the system *is*.

**(1) `create_app` does NOT fire "at run start, before the first agent node executes."** It fires
*inside* the first agent node. The Product Manager **is** the first agent node — there is no
separate `pm_step` any more (M-unify U1 removed it; `grep -n "def pm_step" team_run.py` returns
nothing). Every node, PM included, goes through the one `agent_run_step`, and that step is where the
sandbox is first needed and therefore first created. So the fault is not "something fires too
early"; it is "the very first thing that needs compute cannot get any." Round 1 / PM node is exactly
where you would expect a dead sandbox credential to land.

**(2) "Tvashtr should not be creating Fly.io apps" describes a system Tvashtr is not.** The per-run
Fly app is not a deployment of the user's project and has nothing to do with shipping. It is the
*sandbox the agent runs inside* — one throwaway Firecracker microVM per run, booting
`openhands/agent-server`, on the owner's private network behind a one-way Flycast door and an egress
firewall, destroyed at run end. The design intent is in fact already satisfied: Tvashtr works on the
given GitHub repo and opens a PR (`ship_step` → `push_and_open_pr_step`, git and GitHub only, no Fly
call anywhere in it). The Fly app is *where* that work happens, not *what* it produces.

This matters because it rules out the preferred fix. There is no create_app call to delete.

## 1. Root cause, in three sentences

The deployed app sets `TVASHTR_AGENT_SANDBOX = "fly"` (`fly.toml:37`), which routes every agent node
to `OpenHandsFlyAdapter`, and that adapter creates a per-run Fly app the first time a node needs a
sandbox — which is the PM node, the first node in the graph. The `TVASHTR_FLY_API_TOKEN` secret on
that app is refused by Fly with HTTP 403 on every endpoint including reads of its own machines, so
`create_app` fails, `agent_run_step` fails, and the run dies at round 1 having produced no spec.
Because the failure is three layers below the run view, the UI fell through to its empty-spec
placeholder — "The product manager didn't finish the spec for this run." — which describes the
symptom's shadow rather than the cause.

## 3. Classification: **(a)** — the agents' execution sandbox

Evidence, strongest first:

1. **The mapping is explicit.** `_engine_for_sandbox_mode("fly") == "openhands-fly"`
   (`team_run.py:110`), and that engine name resolves to `OpenHandsFlyAdapter`
   (`registry.py:30-35`), which implements the same `EngineAdapter` contract as the local and Docker
   adapters. It is one of three interchangeable ways to run an agent.
2. **The machine boots the agent runtime.** `machine_config` (`fly_machines.py:493`) sets the image
   to `fly_agent_image` — a digest pin of `openhands/agent-server` — with `init.cmd` of
   `--host 0.0.0.0 --port 8000`, byte-for-byte what `DockerWorkspace` passes in Docker mode. The
   orphan app still on the account confirms it: its machine image is `openhands/agent-server:`.
3. **Production opts in deliberately**, with a written rationale: `fly.toml:34-37` — *"Agent work
   runs in a per-run Fly microVM. The backend is in the SAME org, so it reaches those machines over
   the org's private 6PN network natively."*
4. **Not (c), the ship path.** Shipping is `ship_step` (`team_run.py:1348`) and
   `push_and_open_pr_step` (1378). Both are git/GitHub only; neither touches `FlyMachines`. They run
   *after* the graph walk, not at its start.
5. **Not (b), leftover code.** It is live, deliberate, and maintained across four milestones
   (M-h2a boot, M-h2b suspend/reconstruct/reap, M-h3 egress fence + ceilings, M-h4 region ladder),
   with a dedicated reaper, a scheduled sweep, and four test files covering it.

## 4. Fix taken: **C** — and why A and B were rejected

**A (remove or gate the call) — rejected.** A presupposes classification (b) or (c). It is (a).
There is no vestigial call to delete; removing it removes the compute the agents run on.

**B (make a non-Fly backend the default, put Fly behind an explicit flag) — already true, and
inapplicable to the host that is broken.** Two parts:

- *The flag half is already shipped.* The code default is `docker` (`config.py:179`) and Fly is
  opt-in behind `TVASHTR_AGENT_SANDBOX`. There was nothing to change; production chose `fly`
  explicitly.
- *Flipping production to `docker` would not work.* The deployed image has **no Docker daemon and no
  Docker CLI** — `Dockerfile:32-34` installs only `git` and `ca-certificates`, there is no socket
  mount, and a Fly Firecracker VM provides no daemon. `openhands-docker` would fail at
  `DockerWorkspace` construction, trading a 403 for a different crash in the same node. `local` mode
  would technically run, but it executes the agent **unsandboxed inside the backend process**, on a
  1 GB `shared-cpu-1x` VM that auto-suspends at zero — it discards the containment boundary that
  M-h2a exists to provide, and would run untrusted agent-authored code in the same process as the
  session secrets. Neither is a working alternative *on this host*.

**C (make the dependency explicit; document the exact scope; do not touch credentials) — taken.**
Plus the error-reporting fix the brief required in all three branches. Concretely:

- A **launch pre-flight** that probes the Fly credential at `POST /api/runs` and refuses with a
  clear, named reason **before** a Run row, a DBOS workflow, or a server-side repo clone exists.
- The pre-flight refuses **only** on an unambiguous authorization verdict — no token, or Fly
  answering 401/403. A timeout, 5xx, DNS failure or malformed knob is logged and **allowed
  through**, landing the run exactly where it lands today. That asymmetry is deliberate: being wrong
  permissively costs one run that was going to fail anyway; being wrong strictly turns a 30-second
  Fly blip into a total outage. A pre-flight must not become a new hard dependency.
- The required token **scope** documented where it is configured and where it is set.

### What the user sees now

| | before | after |
|---|---|---|
| when | minutes in, at round 1 | immediately, on the launch button |
| message | "The product manager didn't finish the spec for this run." | "the agent sandbox is unavailable: Fly rejected TVASHTR_FLY_API_TOKEN for org 'personal' (fly list_apps failed: HTTP 403 …). The token is revoked, expired, or was minted against something that no longer exists. Replace it with an org-scoped Fly deploy token (`fly tokens create org`) for org 'personal', with permission to create and destroy apps and machines in it." |
| cost | a Run row, a DBOS workflow, a repo clone, possibly a half-built Fly app | nothing |

No frontend change was needed: the M-legible plumbing already carries a backend refusal to the
launch banner status-agnostically — `errorMessageFromBody` (`api.ts:214`) reads `detail.message`,
wraps it in `ApiError`, and `App.tsx:400` renders `e.message`. I verified this path reads a 503
exactly as it reads the existing 422/429.

| `.env.example` | Same for operators: the exact mint command, the app-vs-org trap, and how to check what is live. |

`HANDOVER.md` and `PROJECTPLAN.md` also show as modified — those edits pre-date this session and are
not mine.

**503, not 422 or 429**, deliberately: 422 is what the neighbouring `_missing_provider_credentials`
raises and is correct *there* (a missing BYOK key is the caller's own account to fix); a dead Fly
token is the operator's deployment credential, so the caller's request is valid and no edit helps.
429 would be worse — it promises the identical request will succeed later, when nothing changes
until a human mints a token.

Because the default sandbox mode is `docker` and `.env` does not override it, the pre-flight is

The 19 new tests cover: `is_authorization_error` accepting 401/403 and rejecting 404 / 500 /
`insufficient_capacity` / transport errors; the pre-flight being inert outside `fly` mode and
constructing no client; a missing token refusing without a network call; 401 and 403 each producing
a blocker naming the env var, the scope and the org; a live token allowing the launch; 500/502/503,
a transport failure and an unexpected exception all **allowing** the launch (the asymmetry);
the token never appearing in the message (`<redacted-fly-token>` instead); and end-to-end,
`POST /api/runs` returning 503 with `code: "sandbox_unavailable"` **and leaving the `runs` table
unchanged**.

Every test binds a fake token to an `httpx.MockTransport` — no socket is opened. This is not
optional hygiene: the Makefile does `include .env` + `export`, so the operator's real Fly token is
ambient in every `make test` process, and a test that built a default client would create real
machines and bill for them. The transport tests drive the **real** `FlyMachines` so the production
`_request` → `FlyApiError` → `is_authorization_error` chain is what is actually exercised.

The happy-path endpoint test deletes its own Run row. Launch tests otherwise leave rows parked in
`running` forever (their workflow is mocked), and that residue accumulates into the M-h3 fleet
ceiling and starts failing live gates elsewhere.

## 8. What Aditya must do manually — exact, copy-pasteable

The code fix does not restore hosted runs. A working credential is required, and per the brief I did
not mint one.

**Step 1 — try the live token you already have.** `tvashtr-mh2-3` is not revoked and does not expire
until 2026-10-18. Confirm it works before minting anything:

```bash
fly tokens list --scope org --org personal          # confirm tvashtr-mh2-3 has no REVOKED AT
```

If you still have that token's value, set it and skip to Step 3. If you do not, go to Step 2.

**Step 2 — mint a fresh org-scoped token.** Org scope, not app scope: an app-scoped deploy token
authenticates fine and still cannot run anything, because the run path's first call *creates* an
app.

```bash
fly tokens create org --org personal --name tvashtr-sandbox --expiry 2160h
```

(`2160h` = 90 days. The default is 20 years; Fly's own docs recommend shorter.)

**Step 3 — set it on the deployed app.** This restarts the machines.

```bash
fly secrets set TVASHTR_FLY_API_TOKEN="FlyV1 <paste>" -a tvashtr
```

**Step 4 — verify, from your laptop, before touching the UI.**

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer FlyV1 <paste>" \
  'https://api.machines.dev/v1/apps?org_slug=personal'
```

`200` means fixed. `403` means the token is still wrong — do not redeploy, re-check the scope.

**Step 5 — delete the orphan (see §10).**

```bash
fly apps destroy tv-run-6ecb87b5-7cf6-453a-9031-1eb67373c9d6
```

**Step 6 — revoke the dead token** once the new one is confirmed working, so this cannot recur from
a stale copy:

```bash
fly tokens revoke RVy7ymKw5Mb9Kiv1nbgXYpnalRCGPKXj9YBjZAjTQJ   # tvashtr-mh2-2, already revoked
```

**Step 7 — set a calendar reminder for ~2026-12-01** (before the 90-day expiry). The pre-flight now
tells you the day it dies instead of blaming the product manager, but it still dies.

Then, on this branch: `make test`, and a hosted run should reach the PM node and proceed.

cost-hygiene backstop (a sweep must never take down startup) but means **the reaper has been failing
silently every ten minutes for as long as the token has been dead.** This is the same root cause
wearing a second hat, and the reason a twelve-week-old orphan is still there.

`tv-run-*` apps exist; `cryptoground-data` is yours and unrelated (the prefix filter makes it

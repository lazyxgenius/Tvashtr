# P1.3b (part 1 of 3) — Ephemeral host ports + crash-resume over the container

> Build via `/tvashtr-loop`. Escalation mode: **halt**. Live targets in-loop: **NOT authorized** (the operator live-runs Docker + LLM). This brief delivers the **ephemeral-port product fix** and the **crash-resume proof over the container**. The forced-escape containment proof and the default flip to `docker` are separate later briefs (parts 2 and 3) — do not touch them here.

---

## Objective
Make the Docker-sandboxed agent path **crash-resumable and reuse-robust** by switching the agent-server container to an **ephemeral host port** (dropping the fixed `8010`), then **prove crash-resume over the container** end-to-end: a `kill -9` mid-agent-run orphans a container; on restart DBOS recovers the run, the boot sweep reaps the orphan, a **fresh** container starts on a **new** port, and the feature ships **exactly once**.

---

## Why (the finding that motivates this)
P1.3a pinned a fixed host port (`agent_server_host_port = 8010`). A P1.3b de-risk smoke surfaced that **Docker Desktop holds the host port for ~30s after a container is torn down** — `docker stop` / `docker rm -f` return long before the host-side port forwarder releases the port. Consequences of a *fixed* port:
- **Crash recovery breaks:** the boot sweep reaps the orphan on `8010`, then the resumed step tries to rebind `8010` while it's still wedged → `RuntimeError: Port 8010 is not available` → recovery fails.
- **Back-to-back runs break:** a second docker run within ~30s of the first collides on `8010` (the first run's `--rm` teardown wedges the port).

Waiting *on* the fixed port does nothing (it's genuinely held the whole time). The fix is to **not reuse the port**: pass `host_port=None` so `DockerWorkspace` picks a fresh free port per container (its `find_available_tcp_port`, range 30000–39999). **Reaping stays by image** (`ancestor=<image>`), which is port-independent, so orphans are still found and removed exactly as today — a fresh container just gets a new port and never waits on the old one's slow release.

This **supersedes the P1.3a fixed-port decision** and **pulls forward only the ephemeral-ports half** of the §15 "ephemeral ports + per-run targeting" item — for a newly-demonstrated serial reason (port-release lag), not the concurrency that item anticipated. **Per-run container targeting stays correctly deferred** (image-based reaping is still right for serial single-operator).

## Smoke reap-lifecycle phase (ephemeral) — what to add to `docker_smoke.py`
After the existing pull-seam exercise + teardown, add a phase that proves the orphan-reap lifecycle against a **real running** container (the one thing the P1.3a smoke never showed — its reap ran before bring-up). Ephemeral version:
- Reap clean-slate (so the proof starts from nothing); print what (if anything) it cleared.
- Bring up one container as an **orphan stand-in** with `host_port=None` (ephemeral). Read `ws._container_id` (a `PrivateAttr`) + `ws.host_port` (the chosen port, for logging).
- Assert `list_agent_containers()` matches the running container via the **`ancestor=<image>`** filter. NOTE the id-width mismatch: `docker run` yields the **full 64-char** id while `list_agent_containers` (`docker ps -aq`) yields **short 12-char** ids — match by **prefix** (`full.startswith(short)`), not equality.
- `reap_agent_containers()` → assert it removed that container and `list_agent_containers()` is now empty (`docker rm -f` is synchronous).
- Bring up a **fresh** container (`host_port=None`) and assert it comes up cleanly — it gets a **different** free port, with **no wait and no collision** (this is the whole point of ephemeral). Tear it down.
- Print a clear `reap-lifecycle OK = True/False` + a summary; exit non-zero on failure; reap in a `finally` so no container is ever left behind. No socket/port-free polling — ephemeral removes the need.

## Crash-harness assertions (precise — IMPORTANT under ephemeral ports)
**Key subtlety:** with ephemeral ports the fresh container gets a *different* port than the orphan, so **the run completes even if reaping silently failed** (no port collision to block it). Therefore the exactly-once outcome proves **crash-resume + idempotent ship**, but does **NOT** prove reaping. Reaping must be proven by **explicit orphan assertions** in the bash harness (the `docker` CLI is already at hand there; keep them out of the Python checker, which can't observe the at-crash state post-hoc):

- **At crash** (after `kill -9` of process1, before process2 starts): assert an orphaned container **EXISTS** — `docker ps -q --filter ancestor=<image>` returns ≥1. *(Proves `kill -9` orphaned a real running container — the precondition for testing reaping. The container is up because the first run_event only fires once the agent is mid-run inside it.)*
- **After recovery** (post-completion): assert **NO** agent-server container remains — `docker ps -aq --filter ancestor=<image>` is empty. *(THE reaping proof under ephemeral ports: the boot sweep reaped the orphan, and the fresh container's `--rm` teardown removed itself.)*
- **(report-only)** grep process2's log for the boot-sweep line (`reaped N orphaned agent-server container(s)`) — confirms the **boot sweep** (lifespan, before DBOS recovery) cleared it, not just reap-before-start; nails the ordering.
- **Durable outcome** via `check_skeleton_crash.py` **unchanged**: workflow → SUCCESS, run → completed, exactly one `ship-{run_id}` tag + commit, one PRD version, one agent-cost row, committed file matches, **≥2 engineer attempts with distinct pids OLD→NEW**.

Harness specifics:
- **Export `TVASHTR_AGENT_SANDBOX=docker`** so BOTH uvicorn processes use the docker adapter (mirror how the local harness exports `TVASHTR_AUTO_APPROVE_GATES=1`; keep auto-approve on so the PRD gate doesn't block the deterministic demo).
- Resolve `<image>` for the filters from settings/config (`agent_server_image`), not a hardcoded literal.
- Mind the container bring-up (~3s) before the first run_event, and **two** bring-ups across the run (process1's, then the resumed process2's). The local harness's 180s first-event / 360s completion windows are a starting point — widen if docker needs it (two-way door; size as needed).

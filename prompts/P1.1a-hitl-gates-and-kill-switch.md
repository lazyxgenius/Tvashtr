# Tvashtr P1.1a — Human-in-the-loop foundation: gates, Tasks-for-Human, and the kill switch (backend)

## Objective
Build Tvashtr's durable human-in-the-loop (HitL) control primitive and validate it on the existing 2-node spine:
1. A **gate** — a workflow pause that creates a **Tasks-for-Human** item and blocks the run *indefinitely* on a DBOS signal until a human resolves it, surviving a crash.
2. A **kill switch** — cancel a run so it stops *and* (unlike a `kill -9`) is **NOT** resurrected by DBOS recovery on the next backend boot.

Prove both by inserting a **PRD-approval gate** between the PM and the Engineer in `run_team`: after the PM writes the PRD the run pauses awaiting human approval; on **approve** it resumes and the Engineer ships; on **reject** it stops without shipping; and a run can be **cancelled** while paused at the gate.

This is **backend + headless validation only**. The Tasks-for-Human UI (panel, resolve/cancel affordances, the "paused" canvas state) is the separate next step (P1.1b) — do **NOT** build any UI here.

## Context
- **Where this fits:** the first step of Phase 1, the foundational control primitive that the cyclic loop (P1.5), the per-loop alignment-check blocker, and the human gate all build on. See `PROJECTPLAN.md` §15 (P1.1) and §17 (the Q1–Q4 + sequencing entries). This step **inlines** the gate into the existing workflow; first-class graph-placed gates come in P1.5.
- **The existing spine (do not regress):** `backend/tvashtr/control_plane/team_run.py::run_team` is one DBOS workflow: `load_team_config_step` → `pm_step` (gateway completion → versioned PRD; sets `Run.pm_document_id`) → `engineer_setup_step` → `engineer_run_step` (the one coarse OpenHands step) → `persist_agent_cost_step` → `ship_step` (git-tag idempotent ship `ship-{run_id}`) → `finalize_run_step`. Started with `DBOS.workflow_id == run_id == str(Run.id)` (via `SetWorkflowID` in `routers.py::create_run`), so every write keys idempotency on `run_id`.
- **Schema (`models.py`):** `Run.status` is currently `pending|running|completed|failed`. `Run` has `pm_document_id`, `ship_commit_sha`, `ship_tag`, `cost_total_usd`. Newest migration is `0005` (`engineer_run_attempts`).
- **HTTP surface (`routers.py`):** `POST /api/runs`, `GET /api/runs/{id}`, `GET /api/runs/{id}/graph`, `GET /api/documents/{id}`, `GET /api/spike/run-events/{id}`. Responses are plain dicts (no ORM/Pydantic coupling).
- **DBOS 2.23.0 primitives — VERIFIED against the installed package (`.venv/.../dbos/_dbos.py`); build to these and confirm the two empirical edges flagged:**
  - `DBOS.recv(topic: str | None = None, timeout_seconds: float = 60) -> Any` — call **inside the workflow**; it is itself a checkpointed step (durable across crashes). **There is no infinite timeout** — pass a large `timeout_seconds` for an "indefinite" gate. **EMPIRICAL EDGE #1 — confirm what `recv` returns on timeout** (likely `None`); the gate must treat a timeout as "still waiting" (re-wait), never as "proceed."
  - `DBOS.send(destination_id: str, message: Any, topic: str | None = None)` — call from **outside** the workflow (the resolve API) with `destination_id = run_id`; delivers the payload that unblocks the matching `recv`.
  - `DBOS.cancel_workflow(workflow_id)` — flips the DBOS workflow status to `CANCELLED`. Recovery only resumes `PENDING` workflows (`_launch` → `get_pending_workflows`), so a `CANCELLED` run is **not** resurrected on reboot — the kill switch and the fix for the P0.5a "abandoned run resurrects" gotcha. **Sync steps are NOT preempted mid-execution** (`@DBOS.step(preemptible=...)` is async-only), so a cancel landing *during* the coarse `engineer_run_step` lets that step finish, then the workflow stops at the next boundary. **EMPIRICAL EDGE #2 — confirm** whether `cancel_workflow` unblocks a `recv`-blocked workflow or only takes effect at the next step boundary; make the cancel path correct **either way** (the run must not progress past the gate and must not ship).
  - `DBOS.set_event`/`get_event` exist but are **not** required — use the `HumanTask` table + `Run.status` as the single source of truth for "what's pending."
- **Standing conventions (load-bearing):** only `gateway/gateway.py` imports `litellm`; only `engines/openhands_adapter.py` imports `openhands.*` (lazily) — **this step touches neither**, and app startup + the offline suite must stay `openhands`-free (a test enforces this). Every side-effecting write inside a `@DBOS.step` is idempotent on a `DBOS.workflow_id`-derived key. Migrations are sequential (`0005` → add `0006`).

## Constraints
- **No UI.** Backend + tests + a make target only.
- **No new heavy imports.** No `litellm`, no `openhands.*`. App startup must still import zero `openhands.*` (keep the boundary test green).
- **Gates are INLINED here, not graph-driven.** Insert the approval gate at a fixed position in `run_team`. Do **NOT** add a `Gate` table or any graph-driven gate placement — that is P1.5.
- **Idempotency:** the gate-open and gate-close writes are `@DBOS.step`s idempotent on `{run_id}`-derived keys (a re-run after recovery must not duplicate a HumanTask or mis-set status). The `recv` itself is DBOS-checkpointed.
- **Keep the spine green:** once a gate is approved, `run_team`'s happy path (idea → PRD → ship) must still work; `make skeleton-run`, `make skeleton-crash`, `make smoke`, `make agent-smoke`, `make test`, `make lint` must all still pass (update the live targets to auto-approve the gate if needed — state which).
- **Verify DBOS against the installed 2.23.0**, not from memory — especially the two empirical edges.

## Tasks (ordered)
1. **Migration `0006` + models (`models.py`):**
   - New `HumanTask` table: `id` (BigInteger Identity PK), `run_id` (Text, indexed), `kind` (Text, e.g. `"gate_approval"`), `priority` (Text: `"high_blocker"|"low_nudge"`), `blocking` (Boolean), `topic` (Text, nullable — the `recv` topic this task gates), `title` (Text), `description` (Text), `status` (Text: `"pending"|"resolved"`), `resolution` (Text, nullable — e.g. `"approved"|"rejected"`), `resolution_note` (Text, nullable), `created_at` (tz), `resolved_at` (tz, nullable). Add a uniqueness scheme that makes gate-open idempotent (e.g. unique `(run_id, topic)`), so the open step is a safe insert-or-return.
   - Extend the documented `Run.status` vocabulary to add `"awaiting_human"` (paused at a gate), `"cancelled"`, and `"rejected"` (gate-rejected terminal). `status` is free Text — no enum migration; update the model docstring.
   - `alembic upgrade head` and `downgrade` must round-trip.
2. **Reusable gate helper (`control_plane/gates.py`):**
   - `open_gate_step(run_id, *, kind, topic, priority, blocking, title, description) -> int` — `@DBOS.step`, idempotently inserts the pending `HumanTask` and (if blocking) sets `Run.status="awaiting_human"`; returns the task id.
   - `close_gate_step(run_id, *, topic, resolution, note) -> None` — `@DBOS.step`, idempotently marks the matching `HumanTask` resolved (`resolved_at`, `resolution`, `resolution_note`) and sets `Run.status="running"`.
   - `wait_at_gate(run_id, topic, *, timeout_seconds, ...) -> dict` — a helper the **workflow** calls: `open_gate_step` → loop `DBOS.recv(topic, timeout_seconds=…large…)`, re-waiting on the timeout sentinel until a real resolution arrives → `close_gate_step` → return the resolution dict. Keep `recv` in the workflow body (do not nest it inside another `@DBOS.step`).
3. **Insert the PRD-approval gate into `run_team`** between `pm_step` and `engineer_setup_step`: topic `f"gate:{run_id}:prd-approval"`, kind `"gate_approval"`, priority `"high_blocker"`, blocking `True`, a human-readable title/description referencing the PRD doc. On resolution:
   - `"approved"` → proceed to the engineer steps + ship as today.
   - `"rejected"` → finalize the run terminal as `"rejected"` (no engineer run, no ship); return `{"status": "rejected"}`.
4. **API (`routers.py`):**
   - `GET /api/runs/{run_id}/tasks` → `{tasks: [...]}` (ordered).
   - `POST /api/runs/{run_id}/tasks/{task_id}/resolve`, body `{decision: "approve"|"reject", note?: str}` → validate the task belongs to the run and is pending; then `DBOS.send(run_id, {"resolution": "approved"|"rejected", "note": note}, topic=<task.topic>)`. Decide who writes the resolved `HumanTask` row — prefer the workflow's `close_gate_step` as the **single writer** (the API only signals); if you also write a marker here, keep the workflow authoritative. State your choice.
   - `POST /api/runs/{run_id}/cancel` → `DBOS.cancel_workflow(run_id)` and set `Run.status="cancelled"` directly (the workflow may not run another step to set it). Return the new status.
5. **Offline test workflow + tests (`tests/`):** add a **minimal gate-only workflow** (no LLM, no agent — e.g. `gate_probe_workflow` that opens a gate, waits, closes, returns the resolution) so the gate/recv/send/cancel/HumanTask machinery is unit-tested with zero `openhands`/LLM. Cover: open → pending HumanTask + `awaiting_human`; resolve/`send` → unblocks + closes (`resolved`, status moves on); idempotent re-run of open/close; `cancel_workflow` → workflow `CANCELLED` + `Run.status="cancelled"`. Keep the existing ≥24 tests and the **no-`openhands`-at-startup** boundary test green.
6. **Live validation (`Makefile` + `scripts/`):** `make hitl-demo` (live; needs `OPENROUTER_API_KEY`; skips cleanly without it like the other live targets), two scenarios against a real backend process:
   - **Approve:** start a run → poll until `Run.status=="awaiting_human"` + a pending HumanTask → `POST …/resolve {decision:"approve"}` → poll until `completed` + `ship-{run_id}` tag exists.
   - **Cancel-at-gate:** start a run → at the gate (`awaiting_human`) → `POST …/cancel` → assert workflow status `CANCELLED`, `Run.status=="cancelled"`, no ship tag; then (mirroring `skeleton-crash`'s real-process harness) restart the backend process and assert the run is **NOT** resumed (stays `cancelled`, never ships). Cancel-at-gate is cheap — it never runs the agent.

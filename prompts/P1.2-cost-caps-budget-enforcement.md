# P1.2 — Cost caps + budget enforcement

> **Brief for `/tvashtr-loop`.** Read this together with `PROJECTPLAN.md` (§13 Risk 3, §15 P1.2, §17) and `HANDOVER.md`. The design below is **locked** (DP-A–D, resolved with the operator) — implement it; do not re-litigate it.

## Loop config
- **Escalation mode: `halt`.** This is a big/important feature (the §13 Risk-3 cost chokepoint, new schema, reuses the P1.1 interrupt path). On any one-way-door decision **not already settled in this brief**, STOP and escalate.
- **Live targets in-loop: NOT authorized.** Run only the offline gates in-loop. The live demo, regressions, and the visual check are operator-run **Human checks** (below) — the agent run is still unsandboxed (the P0.4b write-escape is unfixed until P1.3), so the loop must not run it autonomously.
- **Suggested branch:** `feat/p1.2-cost-caps`.

## Objective
Give every run a **per-run dollar budget**, enforced in the Control Plane, that **pauses the run as a human blocker** when exceeded (approve → continue; reject → stop), with the Model Gateway staying a pure metering chokepoint. Validatable on the existing 2-node spine before the cyclic loop (P1.5) exists.

## Context
The §13 Risk-3 mitigation: layered caps with the Gateway as the single dollar-*metering* chokepoint and enforcement in the **Control Plane** (D2). This is the live, validatable slice of that on the 2-node `run_team` spine. The breach blocker reuses P1.1's gate / `recv` / `send` + Tasks-for-Human machinery (its first non-PRD-gate use of `HumanTask`).

## Resolved design (DP-A–D — implement exactly)

**DP-A — scope & data model.** Per-run cap; per-project deferred (no Project entity in Phase 1 — already registered §15).
- Add to `runs` (migration `0007`): `budget_cap_usd Numeric(12,6) NULL`, `budget_overridden Boolean NOT NULL DEFAULT false`.
- `POST /api/runs` sets `budget_cap_usd` from the request body if provided, else from a new `Settings.default_run_budget_usd`.
- The **live running total is a query, not a stored field**: `COALESCE(SUM(cost_records.cost_usd), 0) WHERE workflow_id = run_id`. Lift `finalize_run_step`'s existing query into a shared `running_cost(run_id) -> Decimal` helper and reuse it in both places. Do NOT maintain a running total on `Run` — `cost_total_usd` stays finalize-only.

**DP-B — enforcement in the Control Plane; gateway stays pure.** Do NOT add run context, DB reads, or budget logic to `gateway.complete()` — it stays a pure request→result function (so the P1.4 proxy swap stays clean).
- New module `backend/tvashtr/control_plane/budget.py` — imports only `dbos` / `sqlalchemy` / `tvashtr.{db,models,metering}` (keep the boundary):
  - `@DBOS.step() budget_check_step(run_id) -> {"over": bool, "spent": float, "cap": float | None}`, where `over = cap is not None and not budget_overridden and spent > cap`. (Pure read — trivially idempotent.)
  - `@DBOS.step() mark_budget_overridden_step(run_id)` sets `budget_overridden = True` (idempotent).
- The check is **reactive / between-steps** — you can't know a call's cost until it returns, so it inspects accumulated *prior* spend and gates the *next* step. A breach can overshoot by ~one step's spend. This is expected; do NOT try to interrupt a step mid-flight (that's P1.4's proxy).

**DP-C — breach pauses as a blocker (reuse P1.1).** In `run_team`, at each spend boundary, call `budget_check_step`; if `over`, open a blocker via the existing `wait_at_gate(...)`:
- `kind="budget_approval"`, `priority="high_blocker"`, `blocking=True`, with a clear title/description ("Over budget: $spent of $cap — approve to continue, reject to stop").
- **Reject →** `finalize_run_step(run_id, status="over_budget")` and return (no ship). **Approve →** `mark_budget_overridden_step(run_id)` and continue (so the rest of the run is not re-gated — "approve = continue to completion").
- Checkpoints (distinct topics so gate-open stays idempotent):
  1. After the PRD gate is approved, **before `engineer_setup_step`** — topic `budget:{run_id}:pre-engineer` ("…before the Engineer runs").
  2. After `persist_agent_cost_step`, **before `ship_step`** — topic `budget:{run_id}:pre-ship` ("…the agent's run exceeded the budget; approve to ship the completed work, or reject to stop").
- New terminal status **`over_budget`** (budget hard-stop, human rejected — no ship). `finalize_run_step` already accepts a status arg; pass `"over_budget"`. Update the `Run.status` docstring vocabulary to include it.

**DP-D — per-call cap IN; ceilings OUT.**
- Add `Settings.default_max_tokens_per_call: int | None = 4096`. In `gateway.complete()`, when `request.max_tokens is None`, apply this default. (The gateway already reads `get_settings()` for fallbacks — this is the same static-config pattern, NOT run state, so the DP-B purity holds.) Callers that set their own `max_tokens` (e.g. the PM's 400) are unaffected.
- Build NO depth/loop/active-agent ceilings (deferred — loop caps are intrinsic to P1.5, recursion/active-agent are Phase 2; already registered §15).

## Scope — OUT (do not build; register in §15 if a named upgrade not already there)

- **Richer budget-breach resolution** (grant-a-specific-increment vs the binary override) — binary is right for the 2-node spine; register this as a new §15 deferred item (*Trigger:* P1.5, when many spend steps exist).

## Frontend (small — reuse P1.1c's Stopped visual)
- `frontend/src/lib/status.ts`: add `over_budget` to the terminal set (`deriveOverall` / `isRunTerminal`), and route it to the muted `stopped` `NodeStatus` in `deriveNodeStatus` (alongside `rejected`/`cancelled`, checked **before** the failed-fold). The run banner reads a legible **"Over budget"**; the node pill reuses the existing **"Stopped"** visual (`.tv-pill--stopped` / `.rf-node--stopped` — NO new CSS, NO ad-hoc hex).
- `frontend/src/lib/api.ts`: add `over_budget` to the run-status type if it's a union.
- `vitest` (`status.test.ts`): cases — over_budget → nodes `stopped` (not `failed`/`idle`); over_budget → terminal; over_budget banner reads the over-budget label (with an explicit `.not.toBe("Shipped")`).

# P0.5a — The Living Canvas (graph-read endpoint + Design-System wiring + React Flow canvas with live node status)

> First of the two P0.5 prompts and the **last major build of Phase 0**. P0.4 proved the resumable 2-node spine end-to-end (PM → Engineer → tagged ship, survives a `kill -9` mid-agent-run). **P0.5a makes that spine *visible*:** a real, attractive canvas that renders the 2-node team and **comes alive as a run progresses** — each node's status updating live by polling. P0.5b (next) adds the document view, the run-event feed, and the M0 exit-criteria walkthrough that formally closes Phase 0.
>
> **This is the first prompt whose bar includes visual/UX quality.** The operator's explicit requirement: **the canvas must be n8n-level (or better)** — clean, attractive, easy to use. Treat the canvas as the centerpiece, not an afterthought.

---

## Objective

Deliver an end-to-end **"start a run and watch the team work"** experience:
1. A read-only backend endpoint `GET /api/runs/{run_id}/graph` returning the team's nodes + edges (so the UI can draw the team).
2. The frontend re-skinned to the **Tvashtr Labs Design System** (warm cream paper, one coral accent, serif/sans/mono type) — the dark placeholder theme is replaced.
3. A polished **React Flow canvas** rendering the 2-node PM → Engineer team with **live, derived per-node status** (idle → running → done / failed), updated by polling `GET /api/runs/{run_id}` every ~1.5–2s.
4. A **"Start the run"** control + a minimal **run banner** (overall status, run id, cost/ship info when present).

No new migration. No changes to the run workflow. Polling, not WebSockets.

## Context

**Where this fits:** the visualization layer over the proven spine. P0.4 built the run but only ever drove it via HTTP/scripts; P0.5a is the first UI that a human watches. After P0.5b, Phase 0 is closed and Phase 1 (Supervisor scoping + a real default team) begins on this same UI foundation — so build the frontend as **real product code**, not a throwaway.

**Current backend state to assume (present + verified through P0.4):**
- **`backend/tvashtr/models.py`** — the schema the UI renders:
  - `TeamGraph(id, name, created_at)`.
  - `AgentNode(id, team_graph_id, role_name, kind, model, engine, position, created_at)` — `kind` ∈ {`"completion"`, `"agent"`}, `engine` ∈ {`"openhands"`, `NULL`}, **`position` is JSONB `{"x":…,"y":…}`** (already populated).
  - `Edge(id, team_graph_id, source_node_id, target_node_id, edge_type, created_at)`.
  - `Run(id, team_graph_id, idea, workflow_id, status, pm_document_id, ship_commit_sha, ship_tag, cost_total_usd, created_at, updated_at)` — `status` ∈ {`pending`,`running`,`completed`,`failed`}.
- **`backend/tvashtr/control_plane/teams.py`** — `build_two_node_team()` inserts one graph with a **PM** node (`role_name="pm"`, `kind="completion"`, cheap `default_model`, `engine=None`, `position={"x":0,"y":0}`) and an **Engineer** node (`role_name="engineer"`, `kind="agent"`, `gpt-4o-mini`, `engine="openhands"`, `position={"x":240,"y":0}`), wired by one `Edge(pm → engineer, edge_type="work")`. **The graph rows only exist once a run is started** (`POST /api/runs` calls this) — there is no standalone "create team" path in P0.5.
- **`backend/tvashtr/control_plane/team_run.py`** — `run_team(idea)` (one DBOS workflow, `workflow_id == run_id == str(Run.id)`). Step order and the **breadcrumbs the UI derives status from**: `load_team_config_step` → `pm_step` (**sets `runs.pm_document_id`**) → `engineer_setup_step` → `engineer_run_step` (the coarse agent step; emits `run_events`) → [on failure: `mark_run_failed_step` sets `status="failed"`] → `persist_agent_cost_step` → `ship_step` (**sets `runs.ship_tag` + `ship_commit_sha`**) → `finalize_run_step` (**sets `status="completed"` + `cost_total_usd`**).
- **`backend/tvashtr/routers.py`** — the HTTP surface the UI consumes (add the new endpoint here, alongside the others, same plain-dict style):
  - `POST /api/runs` (body `{idea?}`) — builds a fresh team via `build_two_node_team()`, inserts the `runs` row `status="running"`, starts `run_team` in the **background** under `SetWorkflowID(run_id)`, returns `{"run_id": …}`. Returns immediately; the workflow runs in the background. **Crucially: the team-graph rows and the run row are created here synchronously, before the workflow does any LLM work — so the graph is renderable the instant `POST` returns, even with no API key (the run just won't progress).**
  - `GET /api/runs/{run_id}` — returns `{run_id, workflow_status, run: {id, team_graph_id, idea, status, pm_document_id, ship_commit_sha, ship_tag, cost_total_usd, created_at, updated_at}, costs:[…]}`. (`workflow_status` is the DBOS status — `PENDING`/`SUCCESS`/`ERROR`/…; `run.status` is our app-level field.) **This single endpoint carries everything the UI needs for live node status + the run banner.**
  - `GET /api/documents/{id}`, `GET /api/spike/run-events/{run_id}`, `GET /api/costs` — for P0.5b, not needed here.
- **`backend/tvashtr/main.py`** — FastAPI + DBOS wiring; CORS is **not** configured and does **not** need to be (the frontend uses the Vite dev proxy — see below).
- Migrations `0001`–`0005`. **P0.5a adds none** (the new endpoint is read-only over existing tables).

**Current frontend state to assume (the P0.1 stub):**

## Constraints

- **Stack / conventions (backend):** unchanged from P0.4 — DBOS 2.23.0, gateway-only `litellm`, adapter-only `openhands` (the new endpoint touches **none** of that; it's a plain SQLAlchemy read), at-least-once-safe writes (N/A here — read-only), plain-dict GET responses matching the existing router style, **verify-don't-assume** for any SDK/library detail.
- **Design System is consumed from the token CSS, not the JS bundle.** Copy the token files into the app; build local TSX components against the token variables. Do **not** `import` or `<script>` the `_ds_bundle.js`, and do **not** reference `window.DesignSystem_dbaa69`.
- **Drop the dark theme.** The app renders on the DS cream/paper theme. No ad-hoc hex colors anywhere — use the DS tokens (semantic aliases preferred). If you reach for a color that isn't in the token set, you're off-brand; stop and use the nearest token.
- **Polling, not WebSockets.** Live updates come from polling `GET /api/runs/{run_id}` on a ~1.5–2s interval. Do **not** add a WebSocket layer (that's a named Phase-1 upgrade). Stop polling on a terminal state (`completed`/`failed`, or workflow `SUCCESS`/`ERROR`/`CANCELLED`/`MAX_RECOVERY_ATTEMPTS_EXCEEDED`). Clean up intervals on unmount.
- **Read-only canvas.** P0.5a renders + lets the user **pan, zoom, fit, select, and drag nodes for layout** — but **NOT author** the graph. Set `nodesConnectable={false}`; no add/delete node, no edge creation. Dragging a node is allowed for feel but its position is **not persisted** (local React state only). Graph *editing* is Phase 2 — do not build editing affordances now.
- **MOTION — governing rule (read carefully).** Achieve n8n-level **polish and usability** (smooth pan/zoom, fit-to-view, MiniMap + Controls, crisp custom nodes, clear hover/select/status affordances) but express a node's **"running"** state and the **"flowing"** edge through the Design System's *calm* vocabulary: a soft coral **tint/ring** on the active node and a one-step coral **weight/colour** change on the active edge. **No perpetual marching-dash edge animation, no bounce, no infinite loops** (the DS forbids "infinite decorative loops"). A single gentle, **bounded** pulse on the active node is acceptable; a never-ending animation is not. (If unsure whether something is too busy, it is — prefer calm.)
- **Re-skin React Flow's chrome.** React Flow's defaults are white panels + blue handles/edges — that is off-brand. Restyle the Background, Controls, MiniMap, edges, and handles to the DS (paper/ink/coral, hairline borders). Do not ship default React Flow styling.
- **Do NOT touch / must keep green:** the backend run logic (`team_run.py`, `shipping.py`, `teams.py`), `models.py`, the existing migrations, and the existing endpoints' behavior. The **only** backend change is **adding** `GET /api/runs/{run_id}/graph` (+ its test) to `routers.py`. All existing make targets must stay green: `test`, `lint`, `crash-demo`, `smoke`, `agent-smoke`, `skeleton-run`, `skeleton-crash`.
- **Read the skills.** This is frontend work to a high bar — **read your built-in `frontend-design` skill** (general quality/aesthetics) **and** `Design System/SKILL.md` (the brand specifics). Both.

## Tasks (ordered)

### 1. Backend — the graph-read endpoint (`routers.py`) + offline test
Add `GET /api/runs/{run_id}/graph`:
- Look up the `Run` by `run_id` (the `workflow_id`/`id` string, consistent with how `GET /api/runs/{run_id}` resolves it). **404** if the run doesn't exist.
- Load the run's `TeamGraph`'s `AgentNode`s and `Edge`s.
- Return (plain dict, matching the router's style):
  ```json
  {
    "run_id": "…",
    "team_graph_id": "…",
    "nodes": [
      {"id":"…","role_name":"pm","kind":"completion","model":"…","engine":null,"position":{"x":0,"y":0}},
      {"id":"…","role_name":"engineer","kind":"agent","model":"…","engine":"openhands","position":{"x":240,"y":0}}
    ],
    "edges": [
      {"id":"…","source_node_id":"…","target_node_id":"…","edge_type":"work"}
    ]
  }
  ```
  UUIDs as strings; `position` passed through as-is; `engine` may be `null`. Order nodes deterministically (e.g. by `created_at`/`id`) so the PM comes before the Engineer.
- **Offline test** (`backend/tests/`, following the existing offline-test harness — TestClient + the test DB, **no LLM, no openhands, no API key, no workflow start**): seed a team graph (call `build_two_node_team()` — it only inserts rows) and insert a `Run` row referencing that `team_graph_id`; `GET /api/runs/{run_id}/graph` and assert the shape — exactly **2 nodes** (roles `pm`/`engineer`; kinds `completion`/`agent`; engines `None`/`"openhands"`; positions `{0,0}`/`{240,0}`) and **1 edge** (`pm → engineer`, `edge_type="work"`). Also assert **404** for an unknown `run_id`. Confirm this test imports **no** `openhands.*` (keep the offline suite openhands-free, per the standing convention).

### 2. Frontend — wire in the Design System (replace the dark theme)
- Copy the DS token CSS into the frontend (e.g. `frontend/src/design-system/` with the `tokens/` subfolder preserved so `styles.css`'s relative `@import`s resolve): `Design System/styles.css` + `Design System/tokens/{fonts,colors,typography,spacing,base}.css`. (Copy `assets/logo/mark-coral.png` into `frontend/public/` or `src/assets/` if you use it in the header.)
- Import the DS into `frontend/src/index.css` alongside Tailwind. **Get the cascade right:** the rendered `body` background must be the DS **paper cream** (`--surface-page`), text the DS **ink**, headings **Newsreader**, UI **Inter** — i.e. the DS base must win over Tailwind v4's preflight. Order the imports / scope as needed so there is **no white or dark body background** anywhere.
- Integrate the tokens with Tailwind v4 cleanly. Either approach is fine as long as the output uses DS tokens (no ad-hoc hex): (a) use the CSS variables directly via arbitrary-value utilities / inline styles (`bg-[var(--surface-card)]`, `style={{color:'var(--text-secondary)'}}`), or (b) map tokens into Tailwind's theme with `@theme inline { … }` to get semantic utilities. Pick the simpler one and be consistent.
- Replace `App.tsx`'s dark shell with an on-brand **app shell**: a calm header (small coral mark + the wordmark "Tvashtr" in Newsreader, sentence-case tagline), the canvas as the main surface, and a restyled backend-reachable affordance. **This step's mini-checkpoint:** `npm run build` passes and the app shell renders on paper with coral accent + serif heading (describe it in the report) — the DS foundation must be solid before the canvas is layered on.

### 3. Frontend — the React Flow canvas (the centerpiece)
- Install **`@xyflow/react`** (React Flow v12 line; **verify the exact installed version** and that it supports React 19 — pin it in `package.json`). Import its **base stylesheet** (`@xyflow/react/dist/style.css`) — required — then layer the DS re-skin on top.
- Fetch the graph from `GET /api/runs/{run_id}/graph` and map it to React Flow `nodes`/`edges` (use the returned `position` directly; **no layout library needed**). Use a custom `nodeTypes` entry for the agent node and (at minimum) DS-styled default edges; a small custom edge is welcome if it helps hit the bar.
- **Custom node component (DS-styled, the thing the eye lands on).** A paper/cream **Card** (`--surface-card`), hairline border (`--border-hairline`), soft 12px radius (`--radius-lg`), generous padding: 
  - the **role** as the title in sentence case (e.g. "Product manager", "Engineer") — Inter medium/semibold;
  - a quiet **caption** line showing the model and (if present) the engine — `--text-secondary`, small;
  - a small on-brand **glyph** (a geometric primitive per the DS — circle/square — or a minimal Lucide icon if you add `lucide-react`; keep it ink-colored, since **coral is reserved for the mark + active state**);
  - a clear **status indicator** (see below).
  - Handles must exist to anchor the edge but stay **visually minimal**; `nodesConnectable={false}`.
- **Per-node status — derive client-side** from the latest `GET /api/runs/{run_id}` payload. **Centralize this in one pure function** (e.g. `deriveNodeStatus(role, run, workflowStatus): "idle" | "running" | "done" | "failed"`) so it's a single source of truth:

  | role | `failed` | `done` | `running` | else `idle` |
  |------|----------|--------|-----------|-------------|
  | **pm** | `run.status==="failed"` && `!pm_document_id` | `!!pm_document_id` | `run.status==="running"` && `!pm_document_id` | (before start / run null) |
  | **engineer** | `run.status==="failed"` | `!!ship_tag` | `!!pm_document_id` && `!ship_tag` && `run.status==="running"` | `!pm_document_id` (waiting on PM) |

  Render each status in the **DS calm vocabulary**: `idle` = quiet stone/hairline; `running` = soft coral tint (`--accent-tint` / `--coral-100`) + coral ring, with at most one **bounded** gentle pulse (no infinite loop); `done` = sage/success treatment (`--success` / `--sage-100`) with a small check; `failed` = brick/danger (`--danger` / `--red-100`). A tiny status label in sentence case ("Working…", "Done", "Waiting", "Failed").
- **The work edge (PM → Engineer).** A clean bezier in `--border-strong`/ink hairline when idle; when the run is **flowing** (PM `done`, Engineer `running`), switch it to **coral** and one step heavier — a **state change, not a perpetual animation**. (If you want a hint of motion, a single bounded transition is OK; no marching dashes.)
- **Canvas chrome for the n8n feel — all re-skinned to the DS:** `<Background>` (subtle dots or fine grid in `--border-faint`/line color on paper — not the default), `<Controls>` (zoom in/out + **fit view**, restyled: paper buttons, hairline borders, ink icons, coral on hover/active — not white/blue), and `<MiniMap>` (restyled to paper/ink/coral; for 2 nodes it's marginal but include it for the "real editor" polish and future-proofing — keep it small/unobtrusive). `fitView` on mount; smooth pan/zoom; `elementsSelectable`; `nodesDraggable` (drag for layout, **not persisted**); `nodesConnectable={false}`.
- **Landing/empty state (DS voice).** Before a run is started there is no graph — show a calm empty state on the canvas surface (e.g. *"Nothing on the loom yet. Start the run and the team appears."* — match the DS voice/microcopy, sentence case, no emoji) with the primary action nearby.

### 4. Frontend — start a run + live polling + run banner
- A primary **"Start the run"** button (DS Button styling — coral primary, sentence case; pick calm copy in the DS voice, e.g. "Start the run"). On click → `POST /api/runs` (empty body uses the pinned default idea) → receive `{run_id}` → `GET /api/runs/{run_id}/graph` to render the team → begin polling `GET /api/runs/{run_id}` every ~1.5–2s.
- Each poll updates the derived node statuses (task 3) and the run banner; the edge reflects flow. **Stop polling on terminal state.** Disable "Start the run" while a run is in flight (DS disabled state ~45% opacity); allow starting a new run once terminal.
- A minimal **run banner** (calm, on-brand): the overall state derived from `workflow_status` + `run.status` ("Running…" / "Shipped" / "Failed"), a short run id, and — when present — `cost_total_usd` and the `ship_tag`/`ship_commit_sha`. Keep it quiet (caption type, hairline-bordered Card) — the canvas is the star.
- **Robustness:** if the run **fails** (e.g. no API key set on the backend, so the PM/Engineer LLM call errors), the UI must degrade gracefully — nodes show `failed`, the banner says "Failed", polling stops, no crash/console spew. (You do not need to make the run *succeed* without a key; just don't break.) Handle fetch errors and the brief window where `run` is `null`. State is in-memory React state; **no `localStorage`**. (Optional nice-to-have: reflect `run_id` in the URL query so a reload can resume polling — not required.)

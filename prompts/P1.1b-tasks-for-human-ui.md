# Tvashtr P1.1b — Tasks-for-Human UI: approve/reject the gate, the kill switch, the "paused" canvas (frontend) + cancel-closes-its-tasks (backend)

## Objective
Make the P1.1a human gate **operable from the UI**: when a run pauses at the PRD-approval gate, surface a prominent **Tasks-for-Human** card to **Approve** or **Reject** it, show the run **paused** on the canvas, and give the operator a **Cancel run** control (the kill switch). Plus a small backend change so cancelling a run **closes its pending gate tasks** (no lying "pending" task on a dead run), and finally **stand up vitest** with unit tests for the (now lifecycle-complete) status derivations.

This is the live, visual counterpart to P1.1a. **Visual/UX quality is part of acceptance** (the n8n-level + Design-System bar from P0.5) — a CLI agent can't fully self-verify the look, so the loop is: you build + typecheck + unit-test + report; the architect reads the FE against the DS; the operator eyeballs the live dev server.

## Context
- **Where this fits:** P1.1b completes P1.1 (the HitL foundation). P1.1a (backend) is **done & verified**: a blocking gate pauses `run_team` between PM and Engineer on `DBOS.recv`; `Run.status` moves `running → awaiting_human → running` (approve) or `→ rejected` (reject); the kill switch is `POST /api/runs/{id}/cancel` (`DBOS.cancel_workflow` → `CANCELLED`, not resurrected). See `PROJECTPLAN.md` §15 (P1.1) + §17 (the P1.1a entry).
- **The P1.1a HTTP surface this UI drives (already built, `backend/tvashtr/routers.py`):**
  - `GET /api/runs/{run_id}/tasks` → `{run_id, tasks: [{id, run_id, kind, priority, blocking, topic, title, description, status, resolution, resolution_note, created_at, resolved_at}]}` (oldest first).
  - `POST /api/runs/{run_id}/tasks/{task_id}/resolve`, body `{decision: "approve"|"reject", note?: str|null}` → signals the workflow; returns `{…, resolution, signaled:true}`. (Validates pending → 404/409.)
  - `POST /api/runs/{run_id}/cancel` → `{run_id, status, workflow_status}`.
  - Existing: `POST /api/runs` (start), `GET /api/runs/{id}` (`{workflow_status, run, costs}`), `GET /api/runs/{id}/graph`.
- **`Run.status` vocabulary (P1.1a):** `pending | running | awaiting_human | completed | failed | rejected | cancelled`. The reject path returns normally so its **`workflow_status` is `SUCCESS`** while `run.status` is `rejected` — the UI must treat **`run.status` as authoritative** for the banner/terminal (else a rejected run reads "Shipped").
- **The current frontend (what you're extending — read these):**
  - `src/App.tsx` — the orchestrator: state (`runId/graph/run/workflowStatus/costs/selectedRole`), a single poll effect (`getRunStatus` every 1800ms while `runId && !terminal`), the toolbar row (Start button + `<RunBanner>`), and `<main>` (canvas + conditional `<SidePanel>`).
  - `src/lib/status.ts` — **the single source of truth for derived status.** `NodeStatus = "idle"|"running"|"done"|"failed"`; `deriveNodeStatus(role, run, wf)`, `deriveOverall(run, wf)` (banner), `isRunTerminal(run, wf)` (stops polling). These currently know only `completed/failed` — **they must learn the full vocabulary.**
  - `src/lib/api.ts` — the typed client (add the three task/cancel calls + a `HumanTask` type here).
  - `src/components/RunBanner.tsx` — the quiet hairline status card in the toolbar (the Tasks card sits near it, more prominent).
  - `src/components/StatusPill.tsx` — dot + label in the DS Badge vocabulary (`tv-pill tv-pill--{status}`); add the new state.
  - `src/canvas/{TeamCanvas,AgentNodeCard}.tsx` — the canvas rebuilds node `status` from `deriveNodeStatus` every poll; `AgentNodeCard` renders `rf-node rf-node--{status}` + a `<StatusPill>`.
  - `src/lib/events.ts` — `summarizeEvent` (pure; flagged untested since P0.5b → a vitest target now).
  - `src/{index.css,canvas.css,panel.css}` — the DS re-skin; pill variants live in the CSS (`tv-pill--running` etc.), node variants (`rf-node--running` etc.). Add the new "paused" variants here, token-driven.
  - `package.json` — scripts are `dev` / `build` (`tsc --noEmit && vite build`) / `preview`; **no test runner yet** — you add vitest.
- **Design System:** read `Design System/SKILL.md` (brand) + your built-in `frontend-design` skill (quality). The "paused / awaiting approval" state and the Tasks card express **attention** in the DS *calm* vocabulary — a soft **coral** tint/ring (the brand accent), **not** an alarming red and **no** infinite marching animation (a single gentle bounded pulse at most). Red stays reserved for `failed`.

## Constraints
- **Tokens only, no ad-hoc hex** (the standing invariant — DS variables or the established `color-mix(var(--…) … , var(--ink-900))` pattern used by the pills).
- **Motion = DS-calm:** no infinite/looping animation; bounded one-shot pulses only; honor `prefers-reduced-motion`.
- **Canvas stays read-only** (`nodesConnectable=false`; no add/delete/rewire) — authoring is Phase 2.
- **`status.ts` stays the single source of truth** — all new status logic goes there (don't scatter status conditionals into components).
- **Backend change is surgical:** only the cancel endpoint (close pending tasks + terminal-guard) + the one unit-test assertion it changes + the documented resolution set. Do **not** touch the gate mechanism, the workflow, or the other endpoints. **No new migration** (the `resolution` column already exists; `"cancelled"` is just another free-text value).
- **Gates of record:** `npm run build` (strict `tsc --noEmit` + `vite build`) must pass, **and** the new `npm test` (vitest) must pass; on the backend, `make test` + `make hitl-demo` must stay green.

## Tasks (ordered)
1. **Backend — cancel closes its pending tasks (+ guard).** In `cancel_run` (`routers.py`): when cancelling, also mark the run's **pending** `HumanTask`s `status="resolved", resolution="cancelled", resolved_at=now()` (a dead run must not leave an actionable task); and **skip `DBOS.cancel_workflow` + the status write if the run is already terminal** (`_TERMINAL_RUN_STATUSES` + `cancelled`) so cancelling a just-completed run can't flip a `completed` run's DBOS status to `CANCELLED`. Update the documented resolution set (`models.py` `HumanTask` comment) to include `"cancelled"`. **Update the one test** in `tests/test_gates.py` (`test_cancel_at_gate_…`) whose assertion currently expects the task to stay `pending` → it should now be `resolved` / `"cancelled"`. Keep all other gate tests + `make hitl-demo` green.
2. **`api.ts` — task/cancel client + types.** Add `HumanTask` (the GET shape above), `getRunTasks(runId) → {run_id, tasks}`, `resolveTask(runId, taskId, decision, note?) → POST`, `cancelRun(runId) → POST {run_id, status, workflow_status}`. Extend the `RunRow.status` comment to the full vocabulary.
3. **`status.ts` — teach the derivations the full lifecycle.** Add `NodeStatus` member `"paused"`.
   - `deriveNodeStatus`: the **Engineer** node is `"paused"` when `run.status === "awaiting_human"` (blocked behind the gate; PM is `done` since `pm_document_id` is set). Keep `done` on `ship_tag`. (A `cancelled`/`rejected` run's not-run Engineer may stay as-is — keep node-state additions minimal; the banner carries the terminal story.)
   - `deriveOverall`: **check `run.status` FIRST** so `rejected`/`cancelled` win over the `workflow_status==="SUCCESS"` shortcut. Map: `completed`→`{done,"Shipped"}`, `awaiting_human`→`{paused,"Awaiting approval"}`, `rejected`→`{failed,"Rejected"}` (or a muted tone), `cancelled`→`{failed,"Cancelled"}` (or muted), `failed`→`{failed,"Failed"}`, else `{running,"Running…"}`. Add `"paused"` to `OverallTone`.
   - `isRunTerminal`: treat `run.status ∈ {completed, failed, rejected, cancelled}` as terminal (so polling stops cleanly after reject/cancel).
4. **`StatusPill.tsx` + CSS — the "paused" indicator.** Add the `paused` label (e.g. "Awaiting approval") and a `tv-pill--paused` + `rf-node--paused` variant in the CSS — soft coral tint/ring, DS-calm (optional single bounded pulse), token-driven.
5. **`TasksForHuman` card (new component).** Given the run's pending **blocking** tasks, render a prominent-but-calm card (coral-tinted) showing the task `title` + `description` (+ `priority`), with **Approve** and **Reject** buttons calling `resolveTask` (an optional small note field is fine, not required). Placed as a **strip attached to the run-banner area** (e.g. directly under the toolbar row, full-width) so a blocker is always visible without a node click — *not* hidden in the node-select `SidePanel`. (Operator-confirmed direction; the dedicated **drawer** is the registered **P1.5** upgrade for when gates land anywhere + multiple tasks coexist — **do not build the drawer now**.)
6. **Cancel-run control.** A **Cancel run** button in the toolbar (next to Start), shown only while `inFlight`, calling `cancelRun`. Guard against accidental clicks (a two-step/confirm affordance — your design judgment; on-brand, no ugly `window.confirm`).
7. **`App.tsx` — wire it.** Fetch tasks in the existing poll effect (so the card appears promptly when the gate opens; same leak-free cleanup, cleared on terminal/unmount); reset tasks on a new run; render the `TasksForHuman` strip + the Cancel button; on approve/reject/cancel, fire the call then **re-poll immediately** (optimistic refresh). After approve the run resumes (poll continues); after reject/cancel it goes terminal (poll stops via the updated `isRunTerminal`).
8. **Stand up vitest + unit tests.** Add `vitest` (devDep) + a `"test": "vitest run"` script (keep `build` as-is — vitest is a separate gate). Unit tests (pure, node env — no jsdom needed) for: `deriveNodeStatus` (incl. the new `paused` engineer state + the existing table), `deriveOverall` (**including that `rejected`/`cancelled` do NOT render "Shipped"**, and `awaiting_human` → "Awaiting approval"), `isRunTerminal` (the new terminal statuses), and `summarizeEvent` (the four payload shapes + the defensive fallback — the P0.5b-flagged gap).

## Acceptance criteria
- `npm run build` clean (strict `tsc` + `vite build`); **`npm test` green** with the new unit tests (status derivations + `summarizeEvent`).
- Backend: `make test` green (incl. the updated cancel-task assertion); `make hitl-demo` green (both scenarios unaffected); no new migration.
- **Live (operator, with a key):** start a run → at the gate the **Tasks-for-Human card** appears with Approve/Reject and the **Engineer node reads "Awaiting approval"** + the banner says so → **Approve** → the run resumes and ships (node → Done, banner → Shipped) → on a fresh run, **Reject** → banner "Rejected", no ship → on another, **Cancel run** → banner "Cancelled", no ship, and the task card clears (no stale pending task).
- No ad-hoc hex; motion is bounded/calm; canvas still read-only.

### The crash design (the one genuinely new bit — detect "mid-iteration-2")

Run the `review_loop` with **`TVASHTR_FORCE_REVISIONS=2`** so the Reviewer returns `changes_requested` for rounds 1 **and** 2, then `approved` at round 3 → the **Engineer runs exactly 3 times** (iterations 1, 2, 3), approving at round 3 *below* the cap (no escalation). Crash **during iteration 2**, detected by the **`EngineerRunAttempt` row count reaching 2**: `engineer_run_step` inserts one attempt row at the start of each iteration, so a 2nd row means iteration 1 completed, the Reviewer returned `changes_requested` (a real loop-back), and iteration 2 is now building. (Optionally also wait for a fresh `run_event` after the 2nd attempt to be sure the agent is mid-call.) Then `kill -9`.

On resume DBOS must: **replay** the recorded Engineer-1, Reviewer-1 (`changes_requested` — the loop-back), and Engineer-2's already-recorded steps up to the crash; **re-run** the in-flight Engineer-2 agent step in the new process; then **continue the loop** — Reviewer-2 (`changes_requested`), Engineer-3, Reviewer-3 (`approved`) — and ship once. So the proof shows the loop **resumes mid-cycle and keeps cycling** post-crash, not merely finishes a last build.

**The keystone** (richer than skeleton-crash): the in-flight iteration re-executed in the new process (an `EngineerRunAttempt` @NEW_PID appears) **while completed iterations did not** — evidenced by the final durable state being **exactly-once per iteration**: `AgentInvocation` Engineer `[1,2,3]` all `done`, Reviewer `[1,2,3]` outcomes `[changes_requested, changes_requested, approved]`, exactly **3** `agent-cost` rows, **one** ship. (`EngineerRunAttempt` has no `iteration` column — confirm in Task 0 — so per-iteration attempt attribution isn't available; the proof leans on the OLD→NEW pid span for re-execution + the exactly-once-per-iteration final state for correct mid-loop resume.)

# P1.5b harness fix — relax the loop targets' shipped-content assertion (cycle/durability proof, not exact-content)

> Architect brief for Claude Code. Tiny, surgical: TWO test-harness files, ONE assertion each. Do NOT touch any product code, any other assertion, or the skeleton checks. Branch `feat/p1.5b-uniform-walk` (the same branch as the P1.5b backend — this folds in; the operator merges).

## Objective
Relax the **shipped-file content assertion** in the review-loop live targets (`loop-run`, `loop-crash`) from **byte-exact equality** to **"the required line is present in the shipped file"**, so a cosmetic edit on a forced-revision round can't fail the cycle/durability proof. Keep every other assertion byte-identical.

## Context — why (this is not masking a bug)
`make loop-run` (`TVASHTR_FORCE_REVISIONS=1`) and `make loop-crash` (`TVASHTR_FORCE_REVISIONS=2`) deliberately drive a **second+ Engineer pass**: the forced Reviewer returns `changes_requested`, handing the Engineer placeholder feedback (`<forced revision: round N of M>`) plus a "revise this IN PLACE" directive. Given nonsense feedback, `gpt-4o-mini` deterministically *tidies* the deliverable — observed: it appends a trailing period, shipping `Shipped by the Tvashtr PM->Engineer team.` instead of `…team`. This reproduced byte-for-byte across two consecutive runs (it's deterministic model behavior, not a flake).

This is **orthogonal to the executor**: `engineer_run_step` (the instruction construction + the revision-round append) is byte-identical to P1.5a, and `make skeleton-run` (no forced revision) ships the exact line cleanly. The loop targets exist to prove **the cycle ran** (`loop-run`) and **the cycle resumes mid-crash** (`loop-crash`) — every structural/durability assertion (Engineer/Reviewer invocation sequences, attempt counts, per-iteration cost rows, exactly-one ship, the OLD→NEW pid re-execution span) is already passing. **Byte-exact content is `skeleton-run`/`skeleton-crash`'s job** (single build, no revision) — those KEEP their strict check. Demanding byte-exact output *after* a synthetic "make changes" round tests the model's restraint, not the executor, so it's over-specified for these two targets.

The relaxed check still catches a genuinely botched deliverable (empty file, wrong content, missing required text) — it only tolerates trailing/cosmetic edits the forced round may introduce.

## The two assertions to change (exact current code)

**1. `scripts/loop_run.py`** — in `main()`, the shipped-file check:
```python
        committed = subprocess.run(
            ["git", "-C", str(ws), "show", f"{tag}:{TARGET_FILE}"], capture_output=True, text=True
        ).stdout
        if committed.strip() == REQUIRED_LINE:
            ok(f"committed {TARGET_FILE} matches required line")
        else:
            fail(f"committed {TARGET_FILE} {committed.strip()!r} != {REQUIRED_LINE!r}")
```

**2. `scripts/check_loop_crash.py`** — the `# --- feature present ---` block:
```python
    content = _git(ws, "show", f"{tag}:{TARGET_FILE}").stdout
    if content.strip() != REQUIRED_LINE:
        fail(f"committed {TARGET_FILE} {content.strip()!r} != {REQUIRED_LINE!r}")
    else:
        ok(f"committed {TARGET_FILE} matches required line")
```

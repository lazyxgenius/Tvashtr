## Outcome (the one thing)
Given a `pair_id` from `POST /api/ab-runs`, the operator sees the **measurable A-vs-B delta**
("which team config ships better") in a side-by-side view, **and** the persisted reviewer
verdict **reasons** appear in the existing single-run Reviewer panel. That completes §14.

## What's already on disk (verify, then build on it)
- `routers.py` `_run_to_dict` already returns per run: `status`, `ship_tag`, `ship_commit_sha`,
  `cost_total_usd`, `idea`, `pair_id`, `pair_label`, `id` (= the run's `workflow_id`).
- `POST /api/ab-runs` already exists and returns `{pair_id, runs:[{run_id, pair_label, team_shape}]}`
  — **A = `two_node`** (no review), **B = `review_loop`** (the agent-Reviewer), both sharing `pair_id`.
- The reviewer **node** is identified in a run's graph by `role_name == "reviewer"` (equivalently
  `config.agent_kind == "reviewer"`), `kind == "agent"`. The **A side (`two_node`) has NO reviewer node**.
- `AgentInvocation` columns (**do not edit the model — read it**): `run_id` (string, == the run's
  `workflow_id`), `node_id` (UUID), `iteration` (int), `status`, `outcome` (str|None — reviewer:
  `approved`/`changes_requested`), `outcome_detail` (Text|None — the verdict **REASONS**, populated
  on a `changes_requested` close, NULL on `approved` and on every non-reviewer close), `started_at`,
  `ended_at`.
- The graph endpoint (`GET /api/runs/{id}/graph`) already returns each node's per-round
  `invocations` list — but **without `outcome_detail`**. Adding it there is the fold-in's data.
- `lib/status.ts` `reviewerVerdictLabel(outcome)` already maps the verdict label + tone (§14.1).
  `lib/api.ts` `NodeInvocation` carries **no** `outcome_detail` yet.
- The frontend is a single **un-routed** `App.tsx`.

**The delta is NOT a sha compare.** Two separate runs always produce different
`ship_tag`/`ship_commit_sha` (different run-ids, separate commits) — so "did A and B ship the
*same* thing" must NOT be read from the sha. Judge the delta from **terminal outcome + review
effort + cost**. A deliverable file-content diff is **out of scope** (a stretch the design marks
"not a v1 gate").

## Tasks (you self-decompose; this is the precise target)

### 1. Backend — `routers.py` ONLY
**1a (the fold-in's data):** in `get_run_graph`, add `"outcome_detail": inv.outcome_detail` to
each dict in the per-node `invocations` list. Additive; every existing key unchanged.

**1b: new `GET /api/ab-runs/{pair_id}`:**
- `select(Run).where(Run.pair_id == uuid.UUID(pair_id)).order_by(Run.pair_label)`. If it returns
  **zero** rows → `raise HTTPException(404, "pair not found")`.
- For each run, build a `side` dict:
  - summary fields: `pair_label`, `run_id` (= `str(run.id)`), `status`, `ship_tag`,
    `ship_commit_sha`, `cost_total_usd` (float|None), `idea`
  - `workflow_status`: `DBOS.get_workflow_status(run.workflow_id).status` (else `"NOT_FOUND"`)
  - find the run's reviewer node:
    `select(AgentNode).where(AgentNode.team_graph_id == run.team_graph_id, AgentNode.role_name == "reviewer")`
    → at most one
  - `team_shape`: `"review_loop"` if a reviewer node exists, else `"two_node"` (derive from the
    graph — do **not** hardcode it by label)
  - `review_rounds`: if a reviewer node exists,
    `select(AgentInvocation).where(AgentInvocation.run_id == run.workflow_id, AgentInvocation.node_id == reviewer_node.id).order_by(AgentInvocation.iteration)`
    → `[{"iteration": i, "outcome": o, "outcome_detail": d}, …]`; else `[]`
- Return `{"pair_id": pair_id, "sides": [ …ordered A then B… ]}`.
- **MUST tolerate a `<2`-run pair** (the §15 single-run-pair caveat — a partial launch failure or
  a runtime-failed side can leave one row): return whatever rows share the `pair_id`; never assume
  two. 404 ONLY when *zero* rows share it.

Response shape (two-run, B mid-cycle then approved):
```json
{
  "pair_id": "…",
  "sides": [
    {"pair_label": "A", "team_shape": "two_node", "run_id": "…", "status": "completed",
     "workflow_status": "SUCCESS", "ship_tag": "ship-…", "ship_commit_sha": "…",
     "cost_total_usd": 0.0021, "idea": "…", "review_rounds": []},
    {"pair_label": "B", "team_shape": "review_loop", "run_id": "…", "status": "completed",
     "workflow_status": "SUCCESS", "ship_tag": "ship-…", "ship_commit_sha": "…",
     "cost_total_usd": 0.0069, "idea": "…",
     "review_rounds": [
       {"iteration": 1, "outcome": "changes_requested", "outcome_detail": "…reasons…"},
       {"iteration": 2, "outcome": "approved", "outcome_detail": null}
     ]}
  ]
}
```

### 2. FE — `lib/api.ts`
- `NodeInvocation` += `outcome_detail: string | null`.
- New interfaces: `ABReviewRound { iteration: number; outcome: string | null; outcome_detail: string | null }`;
  `ABSide { pair_label: string; team_shape: string; run_id: string; status: string;
  workflow_status: string; ship_tag: string | null; ship_commit_sha: string | null;
  cost_total_usd: number | null; idea: string; review_rounds: ABReviewRound[] }`;
  `ABComparison { pair_id: string; sides: ABSide[] }`.
- `startABRuns(): Promise<string>` → `POST /api/ab-runs` (no body → default idea, cheap) → returns `pair_id`.
- `getABComparison(pairId): Promise<ABComparison>` → `GET /api/ab-runs/{pairId}`.

### 3. FE — a NEW pure module `lib/abCompare.ts` (+ `lib/abCompare.test.ts`)
- `isSideTerminal(side): boolean` — terminal when `side.status` ∈ `{completed,failed,rejected,cancelled,over_budget}`
  OR `side.workflow_status` ∈ `{SUCCESS,ERROR,CANCELLED,MAX_RECOVERY_ATTEMPTS_EXCEEDED}` (reuse the
  same sets `status.ts` uses; a side "**shipped**" iff `status === "completed"` AND `ship_tag` is non-null).
- `abHeadline(sides): { headline: string; tone: "delta" | "no-delta" | "diverged" | "pending" }`:
  - `< 2` sides → `"Incomplete pair — only one side launched."` (`diverged`)
  - not all sides terminal → `"Comparison pending — both sides still running."` (`pending`)
  - both shipped, the `review_loop` side had **> 1** review round → e.g. `"Both shipped. The review
    gate sent the build back N−1 time(s) before approving — it caught and corrected something the
    no-review config shipped as-is."` (`delta`)
  - both shipped, the `review_loop` side had **≤ 1** review round → `"Both shipped. The review gate
    ran but didn't change the outcome — no measurable delta."` (`no-delta`)
  - exactly one shipped → `"Diverged — {label} shipped, {label} did not ({status})."` (`diverged`)
- `abCompare.test.ts` covers each branch + the `<2`-side case + a non-terminal case (pure, no fetch).

### 4. FE — the comparison view `components/ABCompare.tsx`
- A "Run A/B comparison" button → `startABRuns()` → hold `pairId` in state.
- Poll `getABComparison(pairId)` every ~1800ms while not all sides terminal (mounted-guarded,
  cleared on terminal/unmount — mirror `App.tsx`'s poll discipline); stop once all terminal.
- Render `abHeadline(sides)`, then the two side cards side-by-side (stack on a narrow width). Each
  card: the config label (`pair_label` + a human `team_shape` — "no review" / "review loop"), a
  status pill (reuse `deriveOverall`'s vocabulary — "Shipped"/"Awaiting approval"/"Over budget"/
  "Failed"/"Rejected"/"Cancelled"/"Running…"; factor a small shared pure helper if clean), shipped
  (`ship_tag` or "—"), cost, and — for the `review_loop` side — the verdict rounds via
  `reviewerVerdictLabel(round.outcome)` with `round.outcome_detail` shown under a
  `changes_requested` round.
- Tolerate `<2` sides + non-terminal sides honestly (show "Awaiting approval" / "Running…").

### 5. FE — `App.tsx` mode toggle
- A minimal segmented control in the existing control bar: **"Single run"** (default) | **"A/B compare"**.
  State only — no router.
- In "A/B compare" mode, render `<ABCompare/>` in `<main>` instead of the canvas/drawer/panel. In
  "Single run" mode the existing view is **unchanged**.

### 6. FE fold-in — `panel/SidePanel.tsx` `ReviewerView`

# P1.1c — "Stopped" node state + resolve-flicker fix

## Objective
Two frontend-only visual fixes to the human-gate screen, both surfaced in the P1.1b live check:
1. A muted **Stopped** node state, so a node that didn't finish because the run was **rejected** or **cancelled** no longer reads as "Waiting" (misleading — looks still-pending on a finished run) or red **Failed** (wrong — nothing failed).
2. Stop the Tasks strip from **flickering the whole canvas** on approve / reject / cancel.

This is the closing step of P1.1 (HitL gates + Tasks-for-Human + kill switch).

## Context
- **Where it fits:** P1.1a (backend gates + kill switch) and P1.1b (Tasks-for-Human UI) are implemented and on disk, **uncommitted**. P1.1c closes P1.1; after it lands + an operator visual re-check, P1.1 is committed.
- **The gate flow** (`backend/tvashtr/control_plane/team_run.py`, read-only here): after the PM writes the PRD, `wait_at_gate` pauses the run (`run.status` → `awaiting_human`). On **approve** the Engineer builds + ships (`run.status` → `completed`). On **reject**, `finalize_run_step(status="rejected")` sets `run.status` → `rejected` and the Engineer step is **never reached** (note: the reject path passes briefly through `running` as the gate un-pauses, then finalizes to `rejected`). The kill switch (`POST /api/runs/{id}/cancel`) sets `run.status` → `cancelled` and closes pending tasks.
- **Frontend status is centralized** in `frontend/src/lib/status.ts` — the single source of truth. `deriveNodeStatus(role, run, workflowStatus)` → per-node status; `deriveOverall` → banner; `isRunTerminal` → polling gate. `StatusPill.tsx` maps status→label. Node visuals: `rf-node--{status}` in `frontend/src/canvas.css`. Pill visuals: `tv-pill--{status}` in `frontend/src/index.css`. Pure-function tests: `frontend/src/lib/status.test.ts` (vitest).
- **`frontend/src/App.tsx`** polls run+tasks every 1.8s via `pull()`, and ALSO calls `pull()` immediately after an approve/reject/cancel (`handleResolve` / `handleCancel`) on top of an optimistic `setTasks`. The Tasks strip (`TasksForHuman`, rendered as a **full-width layout band** above the canvas) shows `pendingTasks = tasks.filter(pending && blocking)`.
  - **Current state to assume:** App.tsx already has the StrictMode `mountedRef` reset fix (the mount effect sets `mountedRef.current = true` and returns a cleanup that sets it false) — **keep it, do not revert**.

### Problem 1 — flicker
On resolve, the strip clears optimistically (canvas jumps up); then the immediate re-poll catches the backend a beat **before** the task is marked resolved (still `pending`) → the strip flashes back (canvas jumps down) → the next poll sees it resolved → clears again. Three layout reflows of a full-width band = the whole canvas flickers.

### Problem 2 — node state
On **reject**, the Engineer never ran, so `deriveNodeStatus` falls through to `idle` → label **"Waiting"** (reads as still-pending on a finished run). On **cancel**, the workflow's `CANCELLED` is folded into `failed` → the node turns **red** (reads as an error, but nothing failed).

## Constraints
- TypeScript strict. `status.ts` stays the single source of truth for derived status.
- Every color a Design-System token or a `color-mix` of one — **no ad-hoc hex**. The Stopped state has **NO motion** (it's terminal/calm); any other motion stays one-shot + `prefers-reduced-motion` guarded.
- **Do NOT touch `deriveOverall` or `isRunTerminal`** — the banner ("Rejected"/"Cancelled") and polling termination are correct and already tested. Only `deriveNodeStatus` changes in `status.ts`.
- **Do NOT change any backend file, migration, or the gate/kill-switch logic.** Frontend-only.
- Don't touch unrelated components (`RunBanner`, `SidePanel`, canvas internals beyond the new node class).
- Keep the flicker fix minimal: a suppression set keyed on task id. No new libraries, no layout-reservation hacks.

## Tasks (ordered)
1. **`status.ts` — add the `stopped` NodeStatus and route reject/cancel to it.**
   - Add `"stopped"` to the `NodeStatus` union (NOT to `OverallTone`).
   - In `deriveNodeStatus`, for **both** roles, insert a check **immediately after** that role's "done" check and **before** the `failed`/other checks:
     `if (run.status === "rejected" || run.status === "cancelled") return "stopped";`
     - PM: right after `if (run.pm_document_id) return "done";`
     - Engineer: right after `if (run.ship_tag) return "done";`
   - This MUST come before the `failed` fold so a `cancelled` run — whose `workflowStatus` is `CANCELLED` (in `WORKFLOW_FAILED`) — reads `stopped`, not `failed`. A **genuine** failure (`run.status === "failed"`, or workflow `ERROR`/`MAX_RECOVERY_ATTEMPTS_EXCEEDED` while `run.status` lags) must STILL return `"failed"`.
2. **`StatusPill.tsx`** — add `stopped: "Stopped"` to `LABELS` (renders dot + label like other non-done states).
3. **`index.css`** — add `.tv-pill--stopped`: muted/neutral, token-driven, clearly NOT coral and NOT red, and visually distinguishable from `.tv-pill--idle` (e.g. a slightly deeper neutral + a defined hairline border). No animation.
4. **`canvas.css`** — add `.rf-node--stopped`: a calm, muted node treatment (e.g. a defined neutral border + a faint neutral wash via `color-mix`), token-driven, NOT coral/red, with **NO** pulse/animation. Should read "concluded without finishing" — distinct from the default idle card and from `--done`/`--failed`.
5. **`App.tsx` — suppress resolved tasks so the strip can't resurrect.**
   - Add `const resolvedIdsRef = useRef<Set<number>>(new Set());`.
   - Change `pendingTasks` to also exclude suppressed ids:
     `tasks.filter((t) => t.status === "pending" && t.blocking && !resolvedIdsRef.current.has(t.id))`.
   - In `handleResolve`, add `taskId` to the set (alongside the existing optimistic `setTasks`).
   - In `handleCancel`, add every currently-pending task id to the set **before** the optimistic `setTasks([])`.
   - In `handleStart`, reset the set (`resolvedIdsRef.current = new Set()`) so a new run starts clean.
   - Keep the immediate `void pull()` calls (now safe — the strip can't come back) and keep the optimistic `setTasks`.
6. **`status.test.ts` — cover the new state.** Add:
   - Engineer on a **rejected** run (`status: "rejected"`, `pm_document_id` set, `ship_tag: null`, workflowStatus `"SUCCESS"`) → `"stopped"`.
   - Engineer on a **cancelled** run (`status: "cancelled"`, `pm_document_id` set, workflowStatus `"CANCELLED"`) → `"stopped"` (NOT `"failed"`).
   - PM on a **cancelled** run with no `pm_document_id` → `"stopped"`; PM on a cancelled run WITH `pm_document_id` → `"done"`.
   - Regression guards that must still pass: a genuine failure — Engineer with `status: "failed"` / workflowStatus `"ERROR"` → `"failed"`; AND the existing "workflow-level `CANCELLED` with `run.status` lagging at `running` → failed" case (run.status `"running"`, workflowStatus `"CANCELLED"` → `"failed"`) stays `"failed"`.
   - Keep all existing assertions green.

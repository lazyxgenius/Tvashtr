# P1.5a (backend) — Fix the mid-loop crash harness's detect-then-kill race

> Tvashtr build prompt. One tightly-scoped fix to a single test harness. The architect (Tvashtr-13) authored this after a live `make loop-crash` run aborted on a timing race (diagnosis below). **The executor and the checker are correct — do not change them.** Report the diff + reasoning; the live re-run is the operator's.

---

## Objective

Make `scripts/loop_crash_demo.sh` land its `kill -9` **mid-cycle reliably**, by killing the instant the loop is detected mid-cycle and asserting the **frozen** post-kill state — instead of asserting a still-running state that races. **Harness-only**: no executor, checker, test, or other-script change.

---

## Context — the observed failure (not a real bug)

A live `make loop-crash` aborted at the crash-state check:

```
STEP E: wait until the Engineer's 2nd iteration has begun (engineer_run_attempts == 2)
engineer_run_attempts == 2  =>  iteration 2 has begun after one real loop-back
iteration-2 agent is mid-call (run_events 7 -> 9)
STEP F: state at crash (expect: exactly 2 attempts both pid=5039, NO ship tag, run not completed)
  attempts=3  distinct_pids=5039  ship_tag='<none>'  run.status=running
ERROR: expected exactly 2 attempts at crash, got 3
```

**Root cause (timing, not correctness):** the deliberately-trivial `greeting.txt` task makes each Engineer iteration ~1 second, so the loop cycles faster than the harness's *detect → wait-for-run_event → check → kill* sequence. After Step E detected `engineer_run_attempts == 2`, the best-effort "wait for a fresh run_event" loop (run_events 7→9) gave the loop ~1–2s to finish iteration 2, get another `changes_requested`, and start iteration 3 (count → 3). Step F then asserted `== 2`, saw 3, and aborted. The frozen state it printed (`attempts=3, run.status=running, ship=<none>`) is itself a **valid mid-loop crash point** — iteration 3 building, two real loop-backs already recorded, nothing shipped. The harness wrongly rejected it.

**Two harness flaws** (and only the harness):
1. The crash-state is asserted **while the loop is still running** (between detection and the kill), so the attempt count races upward.
2. The assertion pins the crash to **iteration 2 exactly** (`== 2`). Catching iteration 2 *or* 3 — any Engineer iteration after at least one loop-back — is an equally valid mid-loop crash.

**Why the checker needs no change:** `scripts/check_loop_crash.py` asserts the *final* state — Engineer `AgentInvocation` `[1,2,3]` all `done`, Reviewer `[changes_requested, changes_requested, approved]`, 3 agent-cost rows, one ship, and `EngineerRunAttempt` count `> 3` spanning `pids[0]==OLD_PID → pids[-1]==NEW_PID`. These hold whether the in-flight (re-executed) iteration was 2 or 3: a crash during iteration 3 yields attempts `[i1@OLD, i2@OLD, i3@OLD, i3@NEW]` (first OLD, last NEW, count 4 > 3); a crash during iteration 2 yields `[i1@OLD, i2@OLD, i2@NEW, i3@NEW]` (same shape). The executor crash-resumes correctly — that is not in question here. **Do not touch the checker or `backend/tvashtr/**`.**

## Tasks (ordered)

1. **Step E — remove the run_event wait entirely.** Delete the best-effort "wait until iteration 2's agent emits a fresh run_event" loop (the `EVENTS_AT_DETECT` / `EVENTS_NOW` block). It is the source of the fatal delay. (You may keep or remove the `event_count` helper if now unused — if removed, ensure nothing else references it.)
2. **Kill the instant the loop is mid-cycle.** Keep the existing poll: `attempt_count` until `>= 2` (≥1 real loop-back recorded ⇒ genuinely mid-cycle), with its timeout + `tail` on failure. The moment it reaches `>= 2`, **immediately `kill -9 "$OLD_PID"`** and wait for the process to die (reuse Step G's `while kill -0 … sleep 0.2; done; CURRENT_PID=""` mechanics) — *before* reading any crash-state. Echo which iteration was caught (e.g. `killed mid-cycle at engineer_run_attempts=$N`).
3. **Assert the FROZEN post-kill state (race-free).** After the process is dead, read the now-stable DB once and assert: `attempt_count >= 2` (the loop was mid-cycle when killed), the `ship-$RUN_ID` git tag is **absent**, and `runs.status` is **not** `completed` (and not any other terminal status — `failed`/`rejected`/`over_budget`/`cancelled`). On any failure, abort non-zero with a clear message. (The process is dead and no replacement is running yet, so the state cannot advance — this is the whole point: no race.)
4. **Re-order the step banners** so they read correctly: detection → kill → frozen-state assertions → restart. (e.g. fold the old Step F/G into "STEP F: kill -9 mid-cycle, then assert the frozen crash-state".) Keep the output informative.
5. **Leave Steps H, I, J unchanged** — restart uvicorn (process 2), poll to `completed` (the 480s loop), and run `scripts/check_loop_crash.py "$RUN_ID" "$OLD_PID" "$NEW_PID" "$BASE"`.
6. *(Optional, only if trivial)* tighten the `attempt_count` poll interval (e.g. `sleep 0.3` instead of `1`) so the kill tends to land during iteration 2 rather than 3 — not required, the checker handles either.

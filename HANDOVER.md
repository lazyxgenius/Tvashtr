## 4. The next slice — and the design calls to make

**HANDOVER §4 sequence (from the brief + the pivot), in order:**

1. **Capability (`kind`) editing — thinker↔worker on a node.** Let the user flip an agent node between `completion` (thinker — a direct LLM call, like the PM) and `agent` (worker — an engine-backed sandboxed run, like the Engineer). This is the next authoring lever: today a node's prompt + model are editable, but its *capability* is fixed at the template's seeding. **Design calls to settle (decide directly from §1 + the pivot, one at a time):**
   - The data: `kind` already discriminates `completion`/`agent` (+ `gate`/`terminal`). Editing it is a column write on an existing field — but flipping `completion`↔`agent` also implies `engine` (`agent` needs `engine="openhands"`; `completion` has `engine=null`). So the edit is a *paired* `kind`+`engine` write, gated to agent/completion nodes (never gate/terminal). Probably extend the `PATCH /api/teams/{id}/nodes/{id}` body (currently `{prompt, model}`) to an optional `capability` (thinker/worker) that maps to `kind`+`engine` server-side — keep the wire vocabulary user-facing ("thinker"/"worker"), not the raw column.
   - **The executor already runs both branches generically** (P1.8a), so flipping `kind` needs NO executor change — `run_graph` dispatches on `kind` and runs `node.prompt` either way. Verify this on disk before scoping (it's the whole reason this slice is cheap).
   - **FE/UX consequence (state it to the operator):** the node-edit panel gains a thinker/worker toggle (a segmented control next to prompt+model); flipping it re-labels the node on the canvas and changes how it runs (a worker gets a sandbox + can touch files; a thinker is a fast pure-LLM step). Decide whether the toggle is on the same panel as prompt/model (likely yes — it's one more authorable field).
2. **Canvas topology editing — `nodesConnectable` ON (the J2 "author your own wiring" differentiator).** Today the canvas is `nodesConnectable={false}` (read-only topology). Turning it on — letting the user draw/delete edges (and add/remove nodes) — is the *core* composability differentiator ("the team is mine"). This is a bigger slice (edge CRUD endpoints + the React Flow connect/delete handlers + validation that the graph stays a valid walk with a start node + terminals). Scope it carefully when reached.
3. **Mid-run prompt re-read** — reuse P1.7's `read_latest_prd_step` read-latest-before-each-use pattern, applied to the node's `prompt` (so editing a node's prompt mid-run reaches the agent on its next node entry). The executor mechanism already exists for the PRD; generalize it to the node prompt.

**Recommendation:** do **capability editing first** — it's the smallest, highest-leverage next lever (one more authorable field, no executor change), and it completes the "a node = {prompt, capability, model}" authoring triple the pivot defines. Topology editing is the marquee differentiator but a meatier slice; sequence it second.

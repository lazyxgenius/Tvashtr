## 5. P1.2 — what it is, and the design points to settle first
**Goal (PROJECTPLAN §15):** layered **cost caps + budget enforcement** with the **Model Gateway as the single dollar chokepoint** — per-call/token caps, **per-run + per-project hard-stops + threshold alerts**, depth/loop/active-agent ceilings; the hard-stop **reuses P1.1's interrupt path** (`cancel_workflow` / the gate-signal machinery). (§13 Risk 3.) Validatable against the existing 2-node spine before the loop exists.

**Genuine open questions to settle (early, with the operator):**
- **Budget data model & scope.** Per-run cap is natural (a column on `Run`, or a config default). **Per-project** caps need a **Project entity that doesn't exist yet** (Phase 1 keeps **Run** as the spine — see Q4/§17). Decide: per-run + a **global/config** ceiling now, with per-project deferred until a Project lands (P1.5/P1.8)? Or introduce a minimal Project sooner?
- **Where enforcement lives & what a breach does.** The Model Gateway (`gateway.complete`) is the pre-call dollar chokepoint — check the running `cost_total` before a call and **block when over**. On breach: **hard-fail the run**, or **pause it as a blocker** (a `high_blocker` `HumanTask` via P1.1's gate, "over budget — approve more or stop")? A **threshold alert** (e.g. at 80%) is a natural **`low_nudge`** task. (P1.1's `HumanTask` already has the `high_blocker`/`low_nudge` field — this is its first non-gate use.)
- **The mid-step agent-spend gap (important — it's *why* P1.4 exists).** In-process caps (P1.2) can hard-stop **our orchestration between steps**, but the agent's own LLM loop bills through the SDK's internal LiteLLM **inside one `@DBOS.step`** and **cannot be interrupted mid-step** by an in-process check (Decision 2, §17). So a runaway *agent* is only bounded by `_MAX_ITERATIONS` until **P1.4 (the LiteLLM proxy)** gives a per-key budget that cuts it off mid-loop. P1.2 should enforce at **our** call sites + **between steps**, and be honest that mid-agent-step enforcement is P1.4's job. Don't try to solve it in-process.
- **Depth/loop/active-agent ceilings** are partly premature (no recursion/loop yet — that's P1.5). Decide how much of the ceiling scaffolding to build now (the *budget* hard-stop is the live, validatable part on the 2-node spine) vs. stub for P1.5.

## 6. Standing conventions (unchanged — still load-bearing)
- **Boundary discipline:** only `gateway/gateway.py` imports `litellm`; only `engines/openhands_adapter.py` imports `openhands.*` (lazily); app startup + the offline suite stay openhands-free (an actual test enforces this). `engines/base.py`'s engine-neutral contract is the durable asset. **`gates.py` keeps the boundary too** — it imports only `dbos`/`sqlalchemy`/`tvashtr.{db,models}`.
- **At-least-once-safe writes:** every side-effecting write inside a `@DBOS.step` is idempotent on a `DBOS.workflow_id`-derived key (`{run_id}:pm-prd-v1`, `{run_id}:agent-cost`, the `ship-{run_id}` git tag, `(run_id, seq)` for events, the gate's unique `(run_id, topic)`). `workflow_id == run_id == str(Run.id)` via `SetWorkflowID`.
- **The gate primitive is reusable:** a run pauses durably on `DBOS.recv(topic, timeout)` (re-wait loop, crash-safe) and resumes on `DBOS.send(run_id, payload, topic)`; `wait_at_gate` opens a `HumanTask` + waits + closes it. **P1.2's budget-breach blocker should reuse this**, not invent a new mechanism. The kill switch (`cancel_workflow` + `Run.status="cancelled"`) is the interrupt path for a hard-stop.
- **Single `OPENROUTER_API_KEY`** for both the gateway and the agent's internal LiteLLM (exported from `.env` by the Makefile). `.env` gitignored; no key has reached a commit; repo has no remote.
- **Verify fast-moving SDKs against the installed package** (e.g. DBOS facts were checked against `.venv/.../dbos/_dbos.py`); **verify Claude Code's reports against the actual files** (reports can arrive scrollback-garbled — read the disk).
- **Frontend:** consume the Design System from the **token CSS** (no `_ds_bundle.js`; **no ad-hoc hex** — tokens or `color-mix` of tokens only). `status.ts::deriveNodeStatus`/`deriveOverall`/`isRunTerminal` is the **single source of truth** for derived status — it now knows the full lifecycle vocabulary (`idle/running/paused/done/stopped/failed`); extend it there, not in components. **Polling (~1.8–2s) is the current transport** (WebSocket = named P1.6 upgrade). The **canvas is read-only** (authoring is Phase 2). Frontend gates: **`npm run build`** (strict `tsc --noEmit` + `vite build`) **and `npm test`** (vitest — now exists; pure-function only so far). Make small fixes directly when faster than a round-trip; substantial work goes through a Claude Code prompt.
- **UI/UX bar = "n8n-level (or better)."** Visual acceptance is a **three-way loop**: Claude Code builds + reports how DS tokens map → architect reads the FE files against the Design System → **operator eyeballs the live dev server**. Don't declare UI "done" on a green build alone — P1.1b proved why (a StrictMode bug passed every headless gate and only the live eyeball caught it).

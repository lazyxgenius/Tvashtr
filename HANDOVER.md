## 5. Part 2 (containment) + part 3 (flip) — design before the brief

### (a) Part 2 — forced-escape containment, the inverse of P0.4b  ← TVASHTR-9'S FOCUS
**Goal:** prove the container is a *real* boundary — force the agent to attempt a write-escape, and assert the **host stays clean**. P0.4b *demonstrated* the escape (local mode: the agent wrote an absolute path that leaked to the host as `backend/greeting.txt`). In docker mode the same absolute write lands **inside the container** (no bind-mount; the pull only reads `/workspace`; the container is torn down with `--rm`) — structurally contained. Part 2 confirms that empirically.

**Design questions to settle with the operator (one at a time):**
1. **How to force the attempt.** The DQ3 reframe tells the agent to write *relative*, so containment needs a **different, escape-attempting instruction** — a test-only instruction (or crafted/"malicious" PRD) that tells the agent to write to an **absolute** path and a **path-traversal** path. P0.4b shows the LLM *does* comply with an absolute-write instruction (it leaked), so this is empirically reliable. Decide where this instruction lives: a test-only override (cleanest — not a config knob the product ships) vs. a flag. *(It must NOT weaken the normal DQ3 instruction.)*
2. **What paths to attempt.** Container-absolute `/escape.txt`; path-traversal from the workspace `../../../escape.txt` (and a deeper one). Optionally a host-style path that wouldn't exist in the container. The point: in docker mode `/escape.txt` is created at the *container's* `/escape.txt` and `../../../escape.txt` resolves *within the container fs* — neither touches the host.
3. **What to assert clean (the containment proof).** The host workspace's PARENT dirs — `backend/`, the repo root, `/tmp`, `$HOME` — wherever a real escape would land on the host. Assert none of the escape files appear there after the run, and that the shipped commit contains **only** the legit relative deliverable (the absolute/traversal files are outside `/workspace`, so the pull never sees them).
4. **⚠️ Avoid a vacuous pass.** If the agent simply refuses or writes nothing, "host is clean" passes for the wrong reason. **Assert positive evidence the attempt actually happened** — e.g. inspect the container fs *before teardown* (`execute_command("test -f /escape.txt")` inside the container shows the file IS there, in the container), or check the agent's event/action stream for the absolute-write action. This makes the proof meaningful: "the agent attempted (and succeeded at) the write, it landed in the container, and the host is clean." **This is the subtle part of part 2 — design it explicitly** (analogous to how part 1's reaping proof needed explicit orphan assertions because the run-outcome alone was insufficient).
5. **The before/after story.** Strongest as a contrast with P0.4b. Decide: does the harness *reproduce* the local-mode leak (run the same escape instruction in `local` mode, show the host file appears, then clean it up) for a full before/after — **or** just prove docker-contains (assert host clean in docker mode only, citing P0.4b for the "before")? Reproducing the local leak writes a real file on the host (needs cleanup) but makes the delta undeniable. Architect's lean: **docker-contains as the core assertion (host clean + positive in-container evidence), with the local reproduction optional** (and self-cleaning if included). Weigh with the operator.
6. **Live-run, operator.** Needs real container + LLM → operator runs `make containment-demo` (likely the new target). Loop builds offline-validated; the operator's run is the acceptance — same pattern as part 1.

## 10. Operator working style (apply throughout)
- **Analogies help** when explaining concepts.
- A message starting with **"By the way"** = give a **short** answer.
- **Procedures one step at a time** — deliver step 1, wait for the reported result, then step 2 (governs commands, installs, the live checks; a checklist of *independent* verifications can be given together). *(Part 1 ran the live checks strictly one-at-a-time — smoke → crash-docker → local regression — and the de-risk smoke caught the ~30s port-hold before the spend.)*
- **Design questions one at a time too** — ask one, wait for the answer, then the next (don't batch the part-2 design questions in §5a).
- **We build via the loop:** one **tight brief per step** (`prompts/`), run via `/tvashtr-loop`; the architect **audits the diffs**. Prefer several tightly-scoped briefs over one sprawling one; a split is fine (P1.1 a/b/c, P1.3 a/b, P1.3b in 3 parts).
- **Decision log over silent revision** — when the operator pushes back or a direction changes, record the reasoning in §17 (part 1's hand-editing correction is recorded there).
- **Operator flags things he doesn't want forgotten** — capture them in the §15 register / §17 immediately.
- **UI/UX quality matters — "n8n-level (or better)";** the operator's live eyeball is the visual gate.
- **Chat naming:** open by stating your name ("This is Tvashtr-9"); the number comes from the first message of the chat.

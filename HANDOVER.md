## 1. What just landed — P1.4a (Tvashtr-11)
The agent's *own* LLM loop (OpenHands) now routes through a **LiteLLM proxy** when enabled — the physical spend chokepoint. As-built (commit in `main` via the FF merge; full detail in the §17 as-built entry):
- **Opt-in** `litellm_proxy_enabled` (default **OFF** → the agent's LLM is built byte-for-byte as before, direct OpenRouter; the 73 offline tests + no-key demos are unaffected).
- An **`agent_llm_routing(settings, model, sandbox_mode)` helper in `config.py`** (openhands-free, shared by both adapters, unit-testable). When ON it returns `{model: "litellm_proxy/<slug>", api_key: <master key>, base_url: <mode-aware proxy URL>}`; when OFF, `{model: <slug>, api_key: OPENROUTER_API_KEY}` (no base_url). Both adapters build their one `LLM(...)` via it, each **hardcoding its own mode** (local→`127.0.0.1`, docker→`host.docker.internal`). The ONLY change inside each adapter is that `LLM(...)` line.
- The proxy as a **docker-compose sibling** to Postgres: image `ghcr.io/berriai/litellm-database:main-stable@sha256:0e8dfd…23b938` (digest-pinned, auto-migrates on boot) + an idempotent **`litellm-db-init`** sidecar (creates a separate `litellm` logical DB on the shared Postgres; the `tvashtr` DB is untouched) + a **wildcard-passthrough `litellm/config.yaml`** (`openrouter/*` → OpenRouter with the one key). `make db-up` now brings up **both** (postgres hard-gates; the proxy warns-not-fails so offline `make test` is never wedged). `scripts/proxy_smoke.py` / `make proxy-smoke` (operator-run de-risk).
- **Untouched:** the gateway/PM path, `metering.py`, `models.py` (no migration), `team_run`, reaping, the `AgentRunResult` shape, the FE. Git merge stat confirmed exactly 12 files, none of the boundary modules.

**Live results (all passed):** `make proxy-smoke` on Docker Desktop 4.68.0/arm64 **retired the #1 risk** — the ad-hoc agent-server container (default bridge, ephemeral port) reached the host-published proxy at `host.docker.internal:4000` → `STATUS 200`, clean teardown. A proxy-enabled docker run shipped `greeting.txt` exactly once (27,988 agent tokens — which *is* the proof the calls flowed through the proxy, since proxy-ON has no fallback path).

**⚠️ Metering finding that corrects a Tvashtr-11 prediction (read this):** the feared "$0 **agent** cost under the proxy" did **NOT** happen — the agent's `gpt-4o-mini` priced correctly through the proxy (`$0.002673`; litellm strips the `litellm_proxy/` prefix and prices the underlying slug). The $0 you'll see is the **PM's** `openrouter/meta-llama/...` (`tokens=211 cost=$0.0`), which is **pre-existing, not a 4a regression** (the PM rides the untouched direct gateway; OpenRouter-priced slugs aren't in litellm's static price map). So P1.2's between-steps gate is **unaffected** by the proxy — the agent (the dominant cost) meters correctly. The metering-collapse (route the PM through the proxy too + make proxy spend authoritative) is **staged in §15**, NOT part of 4b.

## 2. The immediate next step — P1.4b (per-run virtual key + mid-loop cutoff)

### What it is / why
4a put the agent's traffic *through* the proxy but added no enforcement. 4b adds the teeth: a **per-run LiteLLM virtual key with a `max_budget`** is the **hard mid-loop cutoff** P1.2's between-steps gate can't do — when the agent's spend hits the key's budget, the proxy errors **mid-call**, stopping a runaway agent *inside* a single run. This is enforcement only; the metering-collapse stays deferred.

### What's LOCKED (from the §17 P1.4 design entry — Q4)
- The per-run virtual key's `max_budget` = the mid-loop hard cutoff (the proxy errors mid-call).
- On breach, **the adapter classifies the budget error → the run finalizes `over_budget`** (reuse P1.2's existing terminal status), complementary to P1.2's between-steps gate (proxy = mid-step cutoff, gate = between-steps checkpoint).
- Richer "grant-an-increment" breach resolution stays in §15 (don't build it here).
- 4b is **enforcement only**; full metering-collapse is staged (§15).

### Before designing — audit these (the session-opening pattern)
- `backend/tvashtr/routers.py` — **`POST /api/runs`** (where the `Run` is created + `budget_cap_usd` seeded, then `start_workflow(run_team)` under `SetWorkflowID(run_id)`). The natural seam to **mint the per-run virtual key**.
- `backend/tvashtr/config.py` — the `litellm_*` settings + **`agent_llm_routing`** (it currently uses `settings.litellm_master_key` for the agent's api_key; 4b must thread a **per-run key** in instead).
- Both adapters' `LLM(...)` construction (via the helper) — how the per-run key reaches the agent. In docker mode the LLM config (incl. the key) is serialized into the agent-server *inside the container* — the key travels in the config, not the container env (as in 4a).
- `backend/tvashtr/engines/base.py` — **`AgentTask`** (carries `model`/`instruction`/`workspace_dir` today; may need a field to carry the per-run key, or resolve it from run context) and **`AgentRunResult`** (may need a minimal `over_budget` discriminator vs generic `failed` — 4a kept this shape untouched).
- `backend/tvashtr/control_plane/team_run.py` — `engineer_run_step` + the finalize / `mark_run_failed` steps: how a run becomes `over_budget`, and how the adapter's classified budget-error is surfaced up to `finalize_run_step(status="over_budget")`.
- `backend/tvashtr/control_plane/budget.py` — P1.2's `enforce_budget` (the between-steps gate), to compose the mid-loop cutoff with it.
- `backend/tvashtr/models.py` — `Run`: decide if a per-run key handle / proxy-spend column is needed (would be a **migration** — 4a had none).
- `litellm/config.yaml` + the `docker-compose.yml` `litellm` service — the proxy + its `litellm` DB (the virtual-key store, already stood up in 4a).

### Design questions to open with the operator (just-in-time, ONE at a time)
1. **Virtual-key lifecycle.** Mint where/when (at `POST /api/runs`, seeded from the run's budget), how the agent receives it (the per-run key **replaces** the master key in `agent_llm_routing` → the key value must be **threaded from the run into the LLM construction**: a new `AgentTask` field, or resolve from `run_id`), and teardown (delete the key after the run, or let it expire). Note: 4a's master key stays the **admin** credential used to *mint* keys; the per-run **virtual** key becomes the agent's api_key.
2. **The budget number on the key.** The run's full `budget_cap_usd`? The **remaining** budget (cap − already-accrued)? An "agent slice"? And how it composes with P1.2's between-steps cap (avoid conflicting/double limits). The proxy tracks its **own** spend (server-side, in the `litellm` DB) against the key budget — authoritative for the *cutoff*, independent of the telemetry `CostRecord`.
3. **Breach → `over_budget` classification.** The **exact HTTP status + error body** the proxy returns on budget-exceed is an **open question from 4a** (not observable until a key budget exists — capture it live in 4b). Then: how the adapter detects it (inspect the exception) vs a generic LLM failure, and how it surfaces (a flag on `AgentRunResult` → `engineer_run_step` → `finalize_run_step("over_budget")`). Minimal `AgentRunResult` addition.
4. **Key-creation mechanism (verify-don't-assume for the prompt).** Likely the LiteLLM **`/key/generate`** admin API (POST authenticated with the master key; `max_budget`, optional model restriction), called from `POST /api/runs`. Confirm the exact endpoint/payload/auth against the pinned proxy image; the key store is the `litellm` DB.
5. **The demo — `make proxy-budget-demo`.** A tiny per-key budget → the agent's loop hits it → the proxy errors mid-loop → the run surfaces `over_budget`. Needs a docker-mode run with the proxy ON + a tiny key budget. This is the visceral behavioral proof (the felt signal for this stretch).

## M1 — Stall guard (`feat/m01-stall-guard`)

### Changed

Backend only; no migration; no file under `frontend/` or `desktop/`.

- **The brief's premise, corrected on disk:** since M-unify no thinker node calls `gateway.complete`
  — thinkers and workers both run the agent loop through `agent_run_step`. R2 therefore landed in
  two places: the gateway (every `gateway.complete` caller: Query-domain nodes, run-end memory
  distill, node Ask) and the agent path (the mid-run switch).
- `gateway/gateway.py`, `gateway/types.py`, `config.py` — every completion is cut at
  `agent_request_timeout_s` (R1; the limit also rides on the provider call as `timeout=`, and the
  host stops waiting at it on a daemon thread). The primary rides out a 429 / 5xx / connection error /
  timeout with 3 retries at 10 / 20 / 40 s (`TVASHTR_MODEL_RETRIES`, `TVASHTR_MODEL_RETRY_BACKOFF_S`),
  then — or at once on a hard failure — switches ONCE to the per-node backup. The backup gets one
  try. Retries and the switch reach the caller through the new optional `CompletionRequest.on_event`.
- `control_plane/live_state.py` (new) — a running step's live state, derived at read time from its
  newest `run_events`: `running_command` (newest terminal action has no observation; never Quiet),
  `stalled` (no update for `TVASHTR_STALLED_AFTER_S`=300), `quiet` (`TVASHTR_QUIET_AFTER_S`=90),
  `retrying` (newest event is a host `retry`), else `working`; plus `last_event_at`, one plain
  `activity` line, `activity_started_at`, `retry {attempt, of, next_at}`, `backup_model`. A step with
  no events counts from its start. `record_host_event` writes the host's own events (`retry`,
  `backup_model`, `stalled`) in a seq band of their own (1.5e9).
- API (additive): `/api/runs/{id}/graph` nodes gain `live`, the body `live_state`; run payloads
  (`/api/runs/{id}`, the run lists via `run_extras`) gain `live_state` (the run's worst step);
  `/api/inbox` gains `run_stalled` (a live run whose step has had no update for 5 minutes; key
  `run_stalled:<run id>`, comes back after a dismissal when the step's last update changes).
- `control_plane/stall_sweep.py` (new) — a DBOS scheduled workflow (`TVASHTR_STALL_SWEEP_CRON`,
  default every minute; off when `TVASHTR_STALL_SWEEP=0`) ends a step with no update for
  `TVASHTR_STALL_FAIL_AFTER_S` (1200): the invocation and the run fail with `failure_code="stalled"`
  ("The Engineer stopped responding: no update for 20 minutes"), a `stalled` event is written, the
  run's DBOS workflow is cancelled (the walk stops at its next step) and its cached sandboxes are
  closed. The run leaves the in-flight set, which frees its slot. A running command is never swept; a
  run that ended meanwhile is left alone (guarded update).
- `run_failure.py` — the `stalled` code.
- `domain_ask.ask_domain(on_event=…)` + `team_run.domain_query_step_v2` — a Query-domain round
  writes its model call's retries and backup switch on its invocation.
- `team_run._forced_hang` — `TVASHTR_FORCE_HANG_ROLE=<role>` makes that node wait like a model that
  never answers (no adapter, no LLM), released by `close_run_sandboxes` — the live proof's lever.
- `scripts/stall_guard_check.py` + `make stall-guard-check`.
- Tests: `test_stall_guard_gateway.py`, `test_live_state.py`, `test_live_state_api.py`,
  `test_stall_sweep.py`, `test_stall_guard_domain.py`, `test_stall_guard_hang.py`, one case in
  `test_domain_ask_flow.py`; `conftest.py` turns the sweep cron off and the retry backoff to 0.
- Two existing assertions changed, both kept at least as strict:
  `test_node_capabilities.py::test_a_429_on_the_primary_does_NOT_use_the_node_fallback` pinned "a 429
  never switches", which R2 overrides (429×4 → switch); it now pins that three 429s then an answer
  never touch the fallback (4 primary calls, primary serves). `test_domain_query_node_v2.py`'s exact
  `ask_domain` kwargs now also require the new `on_event` hook to be callable, the two kwargs still
  exact.

### Deviations

- A stopped (cancelled) run can be resumed through the API, but no board draws an entry point for it
  (the boards draw the Failed / Stalled callouts and Needs you), so no button offers it; the existing
  Stop dialog's "You can't resume a stopped run." is unchanged (additive only) — a board update is the
  operator's call.
- In a resumed run, the steps carried from the run before are listed as Kept but have no "Resume
  from here" (resume the earlier run for those); the run's own steps do.
- A waiting chip whose previous step was carried can briefly read "Starts after your approval" before
  its step opens (the M2 waiting words, for under a second).
- Board copy: "Resume from the last finished step" opens the step list (the board's flow);
  the Failed callout's Safe sentence reads "your approved spec (v1) is saved" when only the spec is
  carried.
